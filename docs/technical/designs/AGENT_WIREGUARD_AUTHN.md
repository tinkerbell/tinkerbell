# Agent Authentication with WireGuard

Status: proposed

## 1. Problem

Nothing authenticates the Tink Agent to the Tink Server.

- The Agent names itself. Every `GetAction` and `ReportActionStatus` carries an
  `AgentId`, which comes from `worker_id` on the kernel command line. The server
  believes it ([grpc.go](../../../tink/server/internal/grpc/grpc.go)). Anyone who
  can reach the gRPC port can pose as any Agent: they can fetch its Actions,
  including any secrets in Action environment variables, and report false results.
- TLS is optional and authenticates only the server
  ([transport/grpc](../../../tink/agent/internal/transport/grpc/grpc.go)). Without
  it, Actions and their secrets cross the network in plaintext.
- Auto discovery and auto enrollment create Hardware and Workflows for whatever
  `AgentId` asks, so a caller can also create objects.

## 2. Goals

- Authenticate the Agent cryptographically, then authorize each request against
  the Agent's identity and the Workflow it is for.
- A credential that can read or change a Workflow exists only while that
  Workflow has work for the Agent.
- Encrypt all Agent to Tinkerbell gRPC traffic.
- No certificate authority, no certificates to issue or expire, no new external
  service, no new configuration objects, and no new access to Kubernetes Secrets.
- No root, kernel module, or host network changes on the Agent or the server.
- Make takeover attempts visible, and give operators a way to respond.
- Work on machines without a TPM or a pinned key, with no per-boot or
  per-Workflow human step, so it scales to any fleet. There, first contact is
  still trust on first use, as it is today; the design narrows that window and
  makes takeover attempts visible, a modest improvement in security posture.
- Authenticate machines with a TPM by their TPM, including the first
  connection, with no key stored on the machine and no per-boot step.
- Leave room for SPIFFE identities (section 12).
- Enable it gradually: off, optional, then required.

## 3. Non-goals

- Smee's boot path (DHCP, TFTP, iPXE, ISO). Firmware can't run WireGuard.
- The installed OS.
- Agent syslog. It stays plain UDP, attributed by source IP, as today.
- Tootles. Its clients are the installed OS (cloud-init), which has no tunnel,
  so it keeps its plain listener and source IP lookup in every mode.
- The UI and the Kubernetes API, which keep Kubernetes authentication and RBAC.
- The NATS and file transports.
- HookOS, which is deprecated. CaptainOS is the only OSIE this design targets.
- Continuing a Workflow on a new key automatically, except for an Agent
  authenticated by its TPM, whose identity doesn't change with its key
  (section 5.11).
- Proving the attributes an Agent reports (section 5.10).
- mTLS.
- Attestation: proving what software runs on a machine, or that its hardware
  is genuine. TPM authentication (section 5.5) proves which TPM answered, not
  the machine's boot state. Measured boot, PCR policies, and EK certificate
  validation are out of scope; `spec.agent.attestation` is reserved for them
  (section 12).

## 4. Overview

Two layers of WireGuard identity, each with its own server device:

| | Bootstrap | Session |
|---|---|---|
| Agent key pair | Generated by the Agent every boot, or a pinned key pair. The private key stays on the machine. | Generated by the server for one Agent in one Workflow. The private key is sent once over the bootstrap tunnel and not stored. |
| What the server keeps | The public key, in the session record. A pinned key or a TPM's EK hash, set by an operator (section 5.5) | The public key, in the session record |
| Lifetime | One boot, or as long as a pinned key | While the Workflow has work for that Agent |
| Tied to its Agent by | Its **credential** (section 5.5): its WireGuard key, either **trusted on first use**, which binds it for the Workflow, or **pinned** by an operator; or its **TPM**, pinned, which vouches for each boot's key | A **session** in Workflow status |
| Server admits | Any public key, just in time; retained only for a bounded lifetime, with earlier removal for missing or rejected `Register` calls | Only public keys with an active session |
| Reaches | `Register` | `GetAction`, `ReportActionStatus` |

```text
  Smee (iPXE script / ISO kernel cmdline)
    │  all public: bootstrap server public key, UDP endpoint, tunnel prefix
    ▼
  Agent ── loads or generates its bootstrap key pair
    │        private key: never leaves the machine
    │        public key:  what the server sees, binds, or matches
    │        TPM, if any: EK and attestation key, sent as evidence
    │
    │  UDP, WireGuard: bootstrap device
    │  (the handshake proves the Agent holds the private key)
    ▼
  Register(agent_id, evidence) ──► Workflow work for this Agent?
    │      └──► authenticated by the Agent's credential: the pinned key, a
    │           TPM challenge (CHALLENGE, answered on the next poll), the bound
    │           key, or the first to ask? yes: session
    │
    │  ◄── session private key, PSK, session server public key
    │        (the server generates the session key pair, returns the private
    │         key once, and keeps only the public key in Workflow status)
    │
    │  UDP, WireGuard: session device
    │  (admits only session public keys with an active session)
    ▼
  GetAction / ReportActionStatus
    │  interceptor: source address → session public key → session → Workflow, Agent
    ▼
  Agent's work done ──► session public key removed from the device,
                         Agent drops the session private key, back to Register
```

WireGuard's cryptokey routing does the authentication: each Agent public key is
admitted with only its own `/128`, and only the holder of the matching private
key can complete a handshake as that key. WireGuard drops any packet from that
key with a different source address. The source address the server sees is
therefore an authenticated key identity. For `Register`, the server checks that
key against the requested Agent's credential: its binding, its pinned key, or
its TPM, which must vouch for the key (section 5.5).
For session requests, it maps the key to one Workflow and Agent.

**Authentication and authorization are separate layers.**

1. **Authentication** answers "which Agent is this?" It verifies the caller's
   credential, its bootstrap key and, for a TPM, its evidence and its answer
   to a challenge, against the Agent's Hardware, the only source of identity
   (section 5.4).
2. **Authorization** answers "may this Agent run this Workflow now?" from the
   Workflow's Tasks, state, and deadline. A yes is a session: a capability for
   one Agent in one Workflow, until the Workflow's deadline (section 5.8).
3. **Request authorization** checks each `GetAction` and `ReportActionStatus`
   against the session its key holds (section 5.9).

`Register` does the first two; session requests do the third. One coupling is
deliberate: first use binds a key only while a Workflow has work for the Agent,
and keeps the binding in that Workflow's status (section 5.6). Pinned
credentials authenticate without looking at Workflows.

An Agent is bound only while a Workflow has work for it. An idle Agent holds
nothing, so there is no lease to renew or expire, and nothing for an attacker to
take ahead of time.

The building blocks are `pkg/wireguard`, a userspace device built on Tailscale's
[wireguard-go fork](https://github.com/tailscale/wireguard-go) and gVisor's
netstack, a gRPC listener inside the tunnel, and an Agent dialer through it. A
proof of concept on the `authn-poc` branch implements this design end to end.

## 5. Design

Sections 5.1 to 5.3 cover the devices, the bootstrap tunnel, and `Register`.
Then: authentication (sections 5.4 to 5.7), authorization (sections 5.8 and
5.9), the lifecycle of identities, work, and keys (sections 5.10 to 5.12),
and operations (sections 5.13 to 5.16).

### 5.1 Server devices

The WireGuard devices belong to the `tinkerbell` binary, not to one service.
The Tink Server listens inside them.

- Two userspace devices: bootstrap and session. Each has its own private
  key and UDP port, because a wireguard-go device has exactly one private key.
- The devices listen like Tinkerbell's other services: only in the address
  families `--listener-families` serves (IPv4 by default), on a per-family bind
  address that defaults to the global one, with a per-family port.
  wireguard-go's default UDP bind listens on every interface in both families,
  so the server uses its own bind, one socket per configured address. Boot
  parameters for each family advertise that family's endpoint at its public
  address, and `Register` returns the session endpoint in the family the Agent
  connected over.
- The operator provides the keys and the tunnel prefix (section 5.13).
- One ULA `/48`. The bootstrap tunnel uses its first `/64`, the session tunnel
  the second. The server is `::1` in each. The prefix exists only inside gVisor's
  netstack, so it can't conflict with host or provisioning networks.
- Services inside the tunnels:

| Service | Bootstrap device | Session device |
|---|---|---|
| gRPC `:42113` | `AgentService` (`Register`) | `WorkflowService` (`GetAction`, `ReportActionStatus`) |

- There is no TLS inside the tunnels: WireGuard authenticates and encrypts.
  gRPC applies TLS per server, not per listener, so the tunnels are served by a
  gRPC server without TLS credentials, and the plain listener by its own server,
  with TLS when it is configured. Each tunnel listener tags its connections with
  their tier, so one server can serve both tiers and the interceptor (section
  5.9) knows which a request came through.
- The hybrid post-quantum handshake is on for both devices. Both peers must
  agree and there is no fallback, so the Agent always enables it too. The fork
  supports it for lazily created peers (`NewPeerConfig.Hybrid`) and through the
  configuration protocol (`hybrid=true`).

### 5.2 Bootstrap tunnel

The Agent's side:

- The Agent loads its bootstrap private key from `-wireguard-key-file`. If the
  file doesn't exist, it generates an X25519 key and writes it there with mode
  `0600`. It logs the public key at startup. The private key never leaves the
  machine.
- CaptainOS uses `/run/tink-agent/wireguard.key`. `/run` is a tmpfs, so the key
  survives an Agent restart (section 5.11) but not a reboot: each boot gets a new
  key. An Agent with a pinned WireGuard key keeps it elsewhere; a TPM Agent
  doesn't need to, because its TPM identifies it (section 5.5).
- Its bootstrap address is `bootstrap prefix || first 64 bits of SHA-256(public
  key)`. Both sides compute it, so there is no address allocation state.
- It keeps one bootstrap device, and so one UDP source port, for the life of the
  process, because the server answers a peer only at the source it was admitted
  from (below). Before each `Register` it removes and re-adds the server peer,
  so every poll starts with a fresh handshake: the server keeps a bootstrap peer
  only for a short, fixed lifetime, and a session from an earlier poll may no
  longer exist on its side.

Smee writes three public values to the kernel command line, the same way it
writes `grpc_authority` today, and CaptainOS's `tink-agent-setup` passes them to
the Agent:

| Kernel parameter | Agent flag | Value |
|---|---|---|
| `tinkerbell_wg_public_key` | `-wireguard-server-public-key` | Bootstrap server key, base64 |
| `tinkerbell_wg_endpoint` | `-wireguard-server-endpoint` | Bootstrap device UDP `ip:port` |
| `tinkerbell_wg_prefix` | `-wireguard-prefix` | The `/48` |

None of these are secrets. When they are present the Agent ignores
`grpc_authority`. CaptainOS's `tink-agent-setup` will need to handle these new
Agent flags.

The server's side: the bootstrap device's peer-lookup callback
(`device.SetPeerLookupFunc`) runs when an unknown key sends a handshake
initiation that decrypts with the server's private key. It admits the key with
`AllowedIPs` set to its derived `/128` and nothing else, and records
`address → key` for the interceptor. The callback runs synchronously in
handshake processing, so it only reads memory. It admits every key: anyone
with the server's public key, which is public, can trigger it, and keys are
free. Deciding who a key is belongs to `Register` (section 5.3). A TPM
Agent's key is new every boot, so even under the `pinned` policy (section 5.7)
the device can't know the keys to expect. The
device already holds at most 65,536 peers (`MaxPeers` in wireguard-go), so the
design bounds retention rather than relying on that cap to distinguish real
Agents from attackers.

The fork doesn't learn a peer's address from its packets (it has no roaming),
and the lookup callback gets only the public key. A lazily created peer
therefore has no address to answer at unless the lookup supplies one. The server
wraps the device's UDP bind so that each received packet's endpoint implements
the fork's `conn.InitiationAwareEndpoint`: the device reports the initiator's
public key to it right before the lookup, and the lookup returns that endpoint
in `NewPeerConfig.Endpoint`. The peer is fixed to that source for its lifetime.
When an initiation for an existing bootstrap peer arrives from a different
source, after an Agent restart or a NAT rebinding, the server removes the peer
so that the Agent's next handshake retry is admitted at its new source. That
initiation isn't verified yet, so a replayed one can cost a real Agent one
retry, which the fixed lifetimes below already allow for.

Bootstrap peers are just-in-time and live only in the device's memory; nothing
is written to the API:

- **Every bootstrap peer has a fixed maximum lifetime from admission.**
  Handshakes, keepalives, and `Register` calls cannot extend its deadline,
  regardless of the result. At the deadline the server removes the peer and its
  address-to-key mapping. `WAITING` and `GRANTED` peers are subject to this limit
  too. The proof of concept uses 60 seconds; confirm it by measuring handshake
  retries and a bounded `Register` request and response.
- **Peers that never call `Register` are removed after a few seconds** (10 in the
  proof of concept). A real Agent calls `Register` right after its handshake, so
  these peers need not occupy capacity for the full maximum lifetime.
- **Rejected registrations trigger prompt removal.** `NotFound` and
  `PermissionDenied` schedule removal of the peer and its address-to-key mapping
  after a short, bounded grace period (2 seconds) for the error response to
  leave the tunnel. Removing the peer inside the handler before returning could
  prevent delivery of that response. Subsequent requests and handshakes cannot
  postpone removal, and the grace period cannot extend the maximum lifetime.
- **Removal does not change identity ownership.** It does not clear a binding,
  change a pinned credential, or remove a Workflow session. An Agent can reconnect
  with the same bootstrap key on its next poll, requiring another handshake.
  Response delivery is not guaranteed; if removal cuts off a response, the
  Agent reconnects and retries under the normal retry contract.
- **Handshake flood mitigations do not guarantee availability.** Under load,
  wireguard-go requires a
  cookie round trip, which defeats spoofed source addresses, and rate limits
  handshakes per source IP. Fixed lifetimes prevent callers from retaining peers
  indefinitely, but sustained admission of new keys can still exhaust peer
  capacity or shared server resources.

### 5.3 `Register`

Idle Agents poll `Register` instead of `GetAction`. The retry and status-code
contract in [AGENT_SERVER_RETRY.md](AGENT_SERVER_RETRY.md) applies to it as it
does to `GetAction` today.

```proto
service AgentService {
  rpc Register(RegisterRequest) returns (RegisterResponse) {}
}

message RegisterRequest {
  string agent_id = 1;
  AgentAttributes agent_attributes = 2;     // for discovery and enrollment, moved from ActionRequest
  Evidence evidence = 3;                    // what the Agent can prove beyond its WireGuard key (section 5.5)
  ChallengeResponse challenge_response = 4; // answers the previous response's challenge
}

// Evidence is named after the credential type it proves. The tunnel already
// proves the WireGuard key, so a WireGuard credential sends none.
message Evidence {
  string type = 1;   // "tpm"
  bytes payload = 2; // a TPMEvidence for "tpm"
}

message TPMEvidence {
  bytes ek_public = 1;      // the EK public key, PKIX DER
  bytes ek_certificate = 2; // DER, when the TPM has one
  bytes ak_public = 3;      // the attestation key's TPM2B_PUBLIC
}

message RegisterResponse {
  enum State {
    STATE_UNSPECIFIED = 0;
    STATE_WAITING = 1;   // no Workflow work for this Agent yet
    STATE_GRANTED = 2;
    STATE_CHALLENGE = 3; // answer challenge in the next Register
  }
  State state = 1;
  Session session = 2;          // set when GRANTED
  string reason = 3;            // why there is no work, when the server can tell (section 5.8)
  BootstrapServer move_to = 4;  // set by the previous bootstrap key's device (section 5.14)
  Challenge challenge = 5;      // set when CHALLENGE
}

message Challenge {
  bytes payload = 1; // for "tpm", TPM2_MakeCredential's credential blob and encrypted secret
  bytes ticket = 2;  // opaque to the Agent; returned unchanged
}

message ChallengeResponse {
  bytes payload = 1; // for "tpm", the secret TPM2_ActivateCredential recovered
  bytes ticket = 2;
}

message Session {
  string workflow = 1;          // namespace/name
  bytes private_key = 2;        // session key, generated for this session
  bytes preshared_key = 3;
  string address = 4;           // the Agent's session tunnel address
  bytes server_public_key = 5;  // session server key
  string server_endpoint = 6;   // session device UDP ip:port
  google.protobuf.Timestamp expires_at = 7;
  string server_address = 8;    // the server's address inside the session tunnel
}

message BootstrapServer {
  bytes public_key = 1;         // the current bootstrap server key
  string endpoint = 2;          // its bootstrap device UDP ip:port
}
```

The caller's bootstrap key isn't in the request. The server takes it from the
tunnel, so a caller can only register the key it holds.

**Challenges.** A credential needs a challenge only when its type isn't the
tunnel key. For a WireGuard key, first use or pinned, the identity is the bootstrap
key, and the WireGuard handshake already proves the Agent holds it: the
initiation authenticates the Agent's static key with a Diffie-Hellman against
the server's, replayed initiations are rejected, and the session keys depend on
a fresh server ephemeral, so no request arrives without a live peer that holds
the key. A challenge would prove the same key again. A TPM credential is an EK,
which can't take part in the handshake, so it needs one, and so would a future
type whose key is elsewhere (section 12).

A credential that needs a round trip gets it from the polling the Agent already
does: one `Register` returns `CHALLENGE`, and the next answers it. The server keeps no state between the two, so the answer can reach
any replica. The state travels in the ticket instead:

- The ticket holds the expected answer, the agent ID, the EK hash, the
  attestation key's name, the caller's bootstrap key, and an expiry 30 seconds
  out. It is encrypted and authenticated (AES-256-GCM) under a key derived from
  the PSK root (section 5.13). It must be encrypted, not only signed, because it
  carries the answer.
- An answer counts only if its ticket opens, hasn't expired, and names the same
  Agent and the bootstrap key the answer arrives through, and the answer matches.
- A ticket is useless to another key. The server doesn't track used tickets, so
  the same key can answer the same challenge again until the ticket expires,
  which gains it nothing.
- A challenge is issued only when there is something to grant or enroll
  (step 3 below). An Agent with no work gets `WAITING` without one, so idle
  polls cost no TPM operations.

`Register` authenticates the caller, authorizes it, and issues a session.
Authentication finishes only once there is something to grant, so idle polls
stay cheap:

**1. Authenticate: find the identity and its credential.** The Hardware whose
`spec.agentID` is `agent_id` is the Agent's identity (section 5.4), and its
`spec.agent.authentication` names the credential type and whether it is pinned
(section 5.5); without one, the Agent's WireGuard key is trusted on first use. Without Hardware, auto discovery creates it when enabled
(section 5.10). Otherwise only auto enrollment can proceed, or the server returns
`NotFound` and the Agent retries with backoff. What needs no round trip is
checked here: for a pinned WireGuard key, the caller's key must be it, and for
a TPM, the caller's evidence must name the pinned EK. Otherwise the server
returns `PermissionDenied` and counts the failure (section 5.11). Under the
`pinned` policy (section 5.7), an Agent whose Hardware pins no credential is
refused here with `PermissionDenied`, and an unknown one gets `NotFound`
without discovery.

**2. Authorize: find the work.** A Workflow has work for `agent_id` when it is
`PENDING` or `RUNNING` and its current Task, the first one that hasn't
finished, is assigned to `agent_id`. In a Workflow with several Agents, each
Agent gets its session when its own first Task comes up, not while another
Agent's Tasks run before it. Without work, the answer is `WAITING`, or auto
enrollment creates a Workflow (section 5.10). Hardware that opts out of
enrollment (`spec.auto.enrollmentEnabled: false`) also gets `WAITING`: it is a
known Agent with nothing to run, not an error. A Workflow names its Agents only
by `agent_id` in its Tasks; it never says how they authenticate.

**3. Finish authenticating.** With something to grant or enroll, a TPM Agent
gets its challenge, and answers it in its next `Register`. First use finishes
in step 4, where the binding decides. A bootstrap key may be authenticated for
several Agent IDs; each is checked on its own (section 5.6).

**4. Issue a session.** Each Workflow records one session per Agent (section 5.8).

| Session record for this Agent | Result |
|---|---|
| None | Session granted. For first use, this binds the caller's key (section 5.6), if the optional source check passes. `GRANTED`. |
| Bound to this key | Session re-issued with a new session key, replacing the old one. Covers a lost response and an Agent restart. `GRANTED`. |
| Bound to another key | First use: `PermissionDenied`, counted and logged (section 5.11). A pinned credential has already authenticated the caller in steps 1 and 3, so the record moves to the caller's key and the old session key is revoked. This is how a TPM Agent continues after a reboot. `GRANTED`. |

### 5.4 Identity

Authentication verifies an Agent's credential and records it, with the Agent
ID, in the Workflow (section 5.8). Authorization uses only that record; how
the credential was verified doesn't matter to it.

**Every Agent's identity is a Hardware object.** Its `spec.agentID` is the
Agent ID, and its `spec.agent.authentication` is how that Agent proves itself.
That includes Agents that aren't provisioned machines, such as an administrative
Agent that sets up the network. Such an Agent gets a Hardware object with only an
`agentID` and, usually, a pinned credential:

```yaml
kind: Hardware
metadata:
  name: netbox-setup
spec:
  agentID: netbox-setup
  agent:
    authentication:
      wireguard:
        publicKey: <bootstrap public key, base64>
```

- **Workflows only authorize.** A Workflow names its Agents by `agent_id` in its
  Tasks and never says how they authenticate. Creating a Workflow decides what
  runs on an Agent, not who that Agent is.
- **An `agent_id` without Hardware has no identity,** so it is neither
  authenticated nor authorized. Auto discovery and auto enrollment create
  Hardware for Agents they meet (section 5.10); that Hardware pins no
  credential until an operator sets one.
- **Whoever can write Hardware decides how Agents prove themselves; whoever can
  write Workflows decides what they run.**
- **`spec.agent` holds the Agent's settings:** `authentication` today, and
  `attestation`, reserved (section 12). `spec.agentID` stays where it is; moving
  it to `spec.agent.id` is left to a later API version.

### 5.5 Credentials

A credential is what an Agent authenticates with. Two things describe it:

- **Type: what identifies the Agent.**
  - **WireGuard:** its WireGuard bootstrap key, which the tunnel handshake
    proves.
  - **TPM:** its TPM's endorsement key (EK), which vouches for each boot's
    WireGuard key through a challenge in `Register`.
- **Trust: why it is accepted.**
  - **First use:** the first credential to register while a Workflow has work
    for the Agent is accepted and bound for that Workflow (section 5.6).
  - **Pinned:** only a credential an operator set ahead of time.

Every Agent presents a WireGuard key, because every Agent comes through the
bootstrap tunnel; a TPM vouches for that key rather than replacing it.

| Type | Trust | An operator sets | The Agent proves | Its WireGuard key | For |
|---|---|---|---|---|---|
| WireGuard | First use (the default) | Nothing | That it holds the key; the first key to register is bound (section 5.6) | New every boot | Machines without a TPM or persistent storage |
| WireGuard | Pinned | The WireGuard public key | That it holds that key, through the tunnel handshake | The same key every boot | Agents with persistent storage, such as administrative Agents |
| TPM | Pinned | The hash of the TPM's EK | That its TPM holds the EK, through a challenge in `Register` | New every boot | Machines with a TPM |

A TPM trusted on first use is not supported. It is a possible way to enroll
TPMs (section 12).

An operator sets the credential in the Agent's Hardware. The field names the
type, and a pinned value makes it pinned:

```yaml
spec:
  agentID: 3c:ec:ef:4c:4f:54
  agent:
    authentication:
      tpm:
        ekPublicKeyHash: <SHA-256, lowercase hex>    # TPM, pinned
      # wireguard:
      #   publicKey: <bootstrap public key, base64>  # WireGuard, pinned
      # wireguard: {}                                # WireGuard, first use
```

- At most one type is set; validation rejects more. Without
  `spec.agent.authentication`, or with an empty `wireguard`, the Agent's
  WireGuard key is trusted on first use. An empty `tpm` is rejected.
- A pinned credential removes the first-use race: only the pinned key, or a
  key the pinned TPM vouches for, is accepted.
- A pinned credential continues a Workflow after a reboot automatically, and
  changing it hands the Agent over (section 5.11).
- The `pinned` policy (section 5.7) makes a pinned credential mandatory for
  every Agent.

The type names, in lower case, are also the Hardware fields and, for a TPM, the
`Register` evidence type (section 5.3). A future SPIFFE type fits the same way
(section 12).

#### Pinned WireGuard key

The Agent loads its key from `-wireguard-key-file` and logs the public key at
startup. Only that key is accepted. The key file must survive reboots: an Agent
that isn't on CaptainOS, such as an administrative Agent, points the flag at a
mounted Secret or volume. A key in `/run` lasts only one boot, so pinning it
works only until the next reboot.

Pinning a key records the operator's trust in it. Nothing proves where the key
is kept. On a machine with a TPM, a TPM is the better credential: it needs no key
stored on the machine (section 9).

#### TPM

Every TPM 2.0 has an endorsement key (EK), created from a seed fixed at
manufacture. Its private key never leaves the TPM, and it survives TPM clears,
disk wipes, and reinstalls. It can't sign; it can only decrypt, in a protocol
called credential activation. With a TPM, the Agent proves that its TPM holds
the pinned EK, and its WireGuard key stays a fresh key every boot. Nothing is
stored on the machine.

**The pinned value** is the EK public key's hash: SHA-256 of its PKIX
(SubjectPublicKeyInfo) DER encoding, in lowercase hex. That is the value
spire-tpm-plugin pins as `tpm:pub_hash`, so one inventory value serves both
(section 12). The Agent uses the RSA 2048 EK from the TCG default template,
the one TPMs ship certificates for, and logs its hash at startup. With
tpm2-tools:

```sh
tpm2_createek -c ek.ctx -G rsa -u ek.pem -f pem
openssl pkey -pubin -in ek.pem -outform der | sha256sum
```

**The protocol**, carried by `Register` (section 5.3):

1. At startup the Agent opens `/dev/tpmrm0`, creates the EK and an attestation
   key (AK), and logs the EK hash. The AK is a restricted signing key that can't
   leave the TPM (`fixedTPM`, `fixedParent`, `sensitiveDataOrigin`). On every
   `Register` it sends `tpm` evidence: the EK public key, the EK certificate if
   the TPM has one, and the AK's public area.
2. When the requested Agent's credential is a TPM and there is something to grant,
   the server hashes the EK public key and compares it with the pinned hash. On
   a match it checks the AK's attributes, then runs `TPM2_MakeCredential` in
   software: a random secret, encrypted so that only a TPM that holds this EK,
   and has an object with the AK's name loaded, can recover it. It returns
   `CHALLENGE` with the result and a ticket.
3. The Agent recovers the secret with `TPM2_ActivateCredential` and sends it,
   with the ticket, in its next `Register`.
4. The server checks the ticket and the secret (section 5.3). The caller is
   authenticated, and the grant goes ahead as for a pinned key.

**What binds the WireGuard key to the TPM is the tunnel.** The challenge and its
answer travel through the bootstrap tunnel of the key that asked, and the ticket
names that key. So the TPM vouches for that boot's key without signing it.
Answering a challenge for a key it doesn't hold would take the real TPM, which
means running code on that machine.

- A reboot brings a new WireGuard key but the same EK, so a Workflow continues
  after a reboot automatically, on the new key (section 5.11).
- No key is stored on the machine: nothing to seal, to copy off the disk, or to
  rotate.
- EK certificates aren't validated against TPM manufacturer CAs. The pinned hash
  already names one TPM, and a valid certificate alone proves only that a TPM is
  genuine, not which machine it is in. The Agent sends the certificate so that
  validation can be added (section 12).
- Where EK hashes come from is the operator's choice: the Agent's startup log,
  tpm2-tools on the machine, purchase or inventory records, or OEM platform
  certificates, which bind the TPM to the server's serial number (section 12).
- Clearing the TPM doesn't change the EK. Replacing the TPM or the motherboard
  does, and needs a new hash.
- An Agent without a TPM, or with `-tpm=false`, sends no evidence. Evidence from
  an Agent whose credential isn't a TPM is ignored.
- TPM authentication proves which TPM answered, not what software asked
  (section 3). Anything with root on the machine can use its TPM, including
  Actions.

**Authentication, not attestation.** A TPM credential uses a TPM attestation mechanism,
but what it establishes is authentication. The two answer different questions:

- **Authentication: who is this?** "This caller is the Agent whose TPM holds EK
  X." Its result is a verified credential (section 5.4). A TPM answers this,
  as a WireGuard key does.
- **Attestation: what is it, and what state is it in?** In the IETF RATS
  architecture (RFC 9334), an attester produces evidence about its state and a
  verifier appraises it against reference values: measured boot (PCR quotes),
  firmware versions, a genuine TPM (its EK certificate chain), or as-built
  components (OEM platform certificates). This design does none of that
  (section 3).

The vocabulary overlaps. Inside the challenge, credential activation proves that
the attestation key lives in the same TPM as the EK, which TCG calls key
attestation; that is the mechanism, not the result. SPIRE calls all of its join
methods node attestation, including join tokens; Keylime calls the EK and
attestation key step registration, and keeps attestation for quotes. The design
names things by what they establish, so the TPM's EK is pinned under
`spec.agent.authentication`, and `spec.agent.attestation` is kept for appraisal
(section 12).

### 5.6 First-use bindings

A binding says "this key is this Agent, for this Workflow." It's how first use
authenticates: it's for Agents whose Hardware pins no credential (section 5.5). It
isn't a separate object: it is the WireGuard key in the Agent's credential in
Workflow status (section 5.8).

It is the one place where authentication depends on authorization, on purpose:
a binding can only be created while a Workflow has work for the Agent, and it
lives and ends with that Workflow. That is what keeps an idle machine from being
bound ahead of its next Workflow (section 9).

- **An Agent is bound only while a Workflow has work for it.** An idle Agent
  gets `WAITING` and holds nothing. There is no lease, no renewal, and no
  release: a reboot or a new key between Workflows needs nothing cleared, and
  an attacker can't bind a machine ahead of its Workflow.
- **The first session creates the binding.** The first key to call `Register` for
  `agent_id` while a Workflow has work for it is bound. Writes use the
  Workflow's `resourceVersion`, so two replicas can't both win.
- **It lasts until the Workflow ends.** A binding ends when its Workflow reaches
  a terminal state (`SUCCESS`, `FAILED`, `TIMEOUT`) or is deleted, or when an
  operator rebinds (section 5.11). It doesn't expire in the middle of a Workflow,
  however long its Actions run.
- **Bootstrap keys need not be unique across Agent IDs.** A key may be bound or
  pinned for multiple Agent IDs. Each registration must
  independently authenticate as the requested Agent; authenticating as one
  Agent gives no permission for another. Each operational session remains
  restricted to one Agent in one Workflow. A bootstrap-key lookup index can
  return multiple records and does not enforce global uniqueness.

**Conflicts.** Another key calling `Register` for a bound Agent gets
`PermissionDenied`. The server counts the refusal and logs that key and its UDP
source address (section 5.11); it writes nothing to the API. Bindings exist only while a
Workflow is active, so this is never a stale binding left by an earlier boot:
either the Agent's key changed in the middle of the Workflow, or two keys claim
the same Agent.

**No head start.** An Agent that is already waiting when its Workflow appears
has no advantage: it and any other caller race for the first session, and a caller
that polls faster usually wins. Most Workflows start by booting the machine, so
its Agent's key is new either way. A pinned credential removes the race.

**Optional source check.** With `--wireguard-binding-source-check`, a key can be
bound only if its UDP source IP, as seen by the bootstrap device, is one of the
Hardware's `spec.interfaces[].dhcp.ip.address`: the address Smee gives that
machine. An attacker then has to take over that exact address on that segment,
which is the trust Smee relies on today, and from then on the key decides. The
source is the one the bootstrap peer was admitted from (section 5.2); a
completed `Register` shows the caller receives packets there.
Re-issued sessions and rebinds (section 5.11) skip the check. It doesn't apply to
Hardware that `Register` creates through discovery, because the first caller
defines that Hardware. It's off by default because it fails when NAT sits between
the Agent and the server, or when the Agent reaches the server from an address
that isn't in the Hardware's spec. It's meaningful only in Smee's DHCP
`reservation` mode, where that address is the one the machine is given. In
`proxy` and `auto-proxy` modes another DHCP server assigns addresses, so the
Hardware's address may be absent or not the one in use, and the check fails or
can't be configured.

### 5.7 Authentication policy

`--agent-authentication-policy` decides which trust is accepted:

| Policy | Credentials accepted |
|---|---|
| `first-use` (default) | Pinned and first use. An Agent without a pinned credential is bound on first use (section 5.6). |
| `pinned` | Only pinned credentials. An Agent without one can't get a session. |

`pinned` removes trust on first use: every Agent proves itself with something an
operator set. `Register` enforces it: an Agent whose Hardware pins no credential is
refused with `PermissionDenied`, counted as `not_pinned`, and an unknown
one gets `NotFound`. The bootstrap device
still answers every key (section 5.2), because a TPM Agent's key is new every
boot and can't be known ahead of time.

With `pinned`:

- It requires `required` mode. `optional`'s plain path would let Agents without
  a pinned credential in. Tinkerbell refuses to start, and Helm refuses to render,
  otherwise.
- There are no first-use bindings. The source check (section 5.6) never
  applies, and the rebind annotation is ignored (section 5.11): an operator
  changes the pinned credential instead.
- An Agent without a pinned credential never authenticates, so nothing can be
  authorized for it. Two things follow, without settings of their own: auto
  discovery doesn't run, because the Hardware it creates pins no credential,
  and auto enrollment runs only for Hardware with one (section 5.10).
- A machine with a TPM needs only its EK hash, which doesn't change, so it
  needs no per-boot step. A machine without a TPM needs a pinned WireGuard key on
  persistent storage. A diskless machine without a TPM gets a new key every
  boot, so `pinned` doesn't suit it.

### 5.8 Authorization and sessions

Authorization takes an authenticated Agent and decides whether it may run a Workflow now
(section 5.3, step 2). A yes is a session: a capability that lets one Agent run
its Tasks in one Workflow, until the Workflow's deadline. A Workflow whose Tasks
name two Agents has two sessions. The server issues a session when `Register`
has authenticated the caller and found work for it. The Workflow must be initialized
and ready to execute before any session is granted.

The first operational session grant starts the Workflow's execution clock.
In the same atomic Workflow status update as that grant, the server records
`globalExecutionStart` from its clock and sets the existing
`globalExecutionStop = globalExecutionStart + globalTimeout`, unless a stop
was already set, which it keeps: a grant never extends it. Preparation before
the first grant does not consume this budget; session establishment, fetching
the first Action, and execution do. The deadline is fixed for the rest of the
Workflow. Later grants, session re-issuance, and rebinds cannot extend it.

- The clock now starts at the grant, which is before attribute detection and
  image pulls; today it starts at the first Action. Templates with a tight
  `global_timeout` may need more room.
- A Template without a `global_timeout` gets a default of one hour.
- Kubernetes stores `metav1.Time` to whole seconds, so the server truncates the
  grant time to the second before computing the deadline. Otherwise `expires_at`
  in the response would be later than the deadline every replica reads back.
- The Tink Controller enforces the same deadline: with `globalExecutionStart`
  set, it times the Workflow out at `globalExecutionStop` in `PENDING` as well
  as `RUNNING`, requeueing for the deadline in both. (Today the controller
  checks the timeout only in `RUNNING`, and sets `globalExecutionStop` at the
  first Action.) There is one deadline, in one field.

To issue a session:

1. Generate a session key pair.
2. Derive the pre-shared key: `HMAC-SHA256(PSK root, Workflow UID || session
   public key)`. Every session has its own session key, so each pre-shared key
   is unique to one Agent in one Workflow; a re-issued session gets a new one. The
   root is one of the server keys (section 5.13), so every replica can compute it
   without the pre-shared key being stored.
3. Write the session record to Workflow status, using `resourceVersion` so only
   one session per Agent wins. Set `expiresAt` to the Workflow's execution
   deadline. For the first grant, establish the execution timestamps in this
   same update. If concurrent grants conflict, retry against the recorded
   deadline rather than starting another clock. Do not grant or re-issue a
   session at or after that deadline:

```yaml
status:
  globalTimeout: 7200
  globalExecutionStart: "2026-10-22T20:10:00Z"
  globalExecutionStop: "2026-10-22T22:10:00Z"   # the fixed execution deadline
  agents:
    - agentID: 3c:ec:ef:4c:4f:54
      credential:                          # what the Agent authenticated with
        type: TPM                          # WireGuard or TPM
        trust: Pinned                      # FirstUse or Pinned
        wireguard:                         # every Agent: the key holding the session;
          publicKey: <base64>              #   for first use, the binding (section 5.6)
          endpoint: 192.0.2.10:41641       # UDP ip:port it registered from
        tpm:                               # set when type is TPM: the TPM that vouched for the key
          ekPublicKeyHash: <hex>
        authenticatedAt: "2026-10-22T20:10:00Z"
      session:                             # what authorization granted
        publicKey: <base64>                # the session public key
        address: fdxx:xxxx:xxxx:1:hhhh:hhhh:hhhh:hhhh
        issuedAt: "2026-10-22T20:10:00Z"
        expiresAt: "2026-10-22T22:10:00Z"  # globalExecutionStop
        revokedAt: null                    # set when the session key is revoked early
```

The credential is a union: `type` names it, `wireguard` is always set, because
every Agent proves a WireGuard key, and `tpm` is set exactly when `type` is
`TPM`. A future type adds a member the same way.

4. Return the private key and pre-shared key, together with the session
   device's public key, endpoint, and tunnel address, in the response. The
   server doesn't store the private key anywhere.

The session address is derived from the session public key, like the
bootstrap address. The session device's peer-lookup callback admits a key
only if an active session in the session index names it, with that session's
`/128`, pre-shared key, and the hybrid handshake. Every replica builds the index
from its Workflow informer. The replica that grants a session also indexes it
as soon as its write succeeds, so the Agent's first handshake isn't dropped
while that replica's cache catches up. On other replicas the handshake is
dropped until their cache has the session, and WireGuard retries it every 5
seconds.

A session's key is removed when:

- **its Agent's last Task in the Workflow finishes,**
- **the Workflow enters `POST`, `SUCCESS`, `FAILED`, or `TIMEOUT`, or is
  deleted,**
- **`expiresAt` passes,** or
- **an operator hands the Agent over** (section 5.11), or
- **a re-issued session replaces it.**

`expiresAt` in status and `expires_at` in the response are an authoritative
upper bound, not a hint or a promise of access until that time. Every session
in the Workflow has the same expiry, including sessions issued to later Agents
and replacement sessions. Earlier revocation can shorten a session's validity.
There is no separate session timeout or renewal.

At the execution deadline the Workflow times out, even if no Action has started.
Every replica independently rejects session admission and authorization at or
after `expiresAt` and removes the peer, without waiting for a Workflow timeout
update. This also prevents a delayed timeout transition from extending access.

Every replica watches Workflows, through an event handler on the Workflow
informer the Tink Server already runs, and revokes a key when its session ends.
Revocation is immediate: the interceptor refuses the key from then on. The peer
itself is removed after a short grace period (15 seconds in the proof of
concept), so that the Agent's next request gets an answer instead of timing out,
and it returns to `Register` promptly. A replica stops accepting an
early-revoked key when its Workflow cache sees the change, so a lagging replica
accepts it a little longer, but never past its recorded expiry. A leaked session
key is useless once removed, and never works for another Workflow or another
Agent.

The Agent learns why its session ended:

- During the grace period, requests on a revoked session get
  `Unauthenticated: session ended: <reason>`: the Workflow is `TIMEOUT`,
  `FAILED`, or `SUCCESS`, was deleted, passed its execution deadline, has no
  Tasks left for this Agent, or the Agent was rebound to another key.
- `Register`'s `WAITING` response carries a `reason` when the caller's key last
  had a session in a Workflow that has ended. The server reads it from the
  Workflow, so it is accurate however long after the revocation the Agent asks,
  and it is only given to the key that held that session.
- The Agent logs the reason once when its session ends, not on every idle poll.

**Reports after a session ends.** An Agent may still be running an Action when
its session ends, for example when the Workflow times out. Its report can then no
longer be delivered, and the Agent drops it and logs why. Nothing is lost: the
Workflow has already ended, and today the server accepts but ignores a final
report for an ended Workflow. The Agent does not cancel the running Action at
the deadline; an Action still ends only at its own timeout. The Agent checks the
expiry with its own clock, so a clock running ahead can make it drop a report
slightly early; it never extends access, because the server enforces the
deadline with its own clock.

The Agent's record stays in Workflow status after its session key is removed.
With first-use trust, `credential.wireguard.publicKey` is the binding, so until
the Workflow ends only that key can be granted again, after an Agent restart.
Another key, such as the next boot's generated key, is refused (section 5.11).
With a pinned credential, the pin decides, and the WireGuard key only records
which key holds the session.

The Agent keeps its session up until the server removes the key. It polls
`GetAction` on the session, including while another Agent's Tasks run between
its own, and doesn't call `Register`. It returns to `Register` only when
requests on the session fail, which is what happens once the key is removed,
and learns there whether it has another session.

### 5.9 Request authorization

An interceptor runs on every request that arrives through a tunnel. It finds the
key from the source address, then applies:

| Request | Arrives on | Allowed when |
|---|---|---|
| `Register` | Bootstrap | Always reaches the handler, which applies section 5.3 |
| `GetAction` | Session | The key's session is active and `AgentId` equals the session's `agentID`. Only the session's Workflow is served. |
| `ReportActionStatus` | Session | Same, and the report names the session's Workflow and a Task assigned to that Agent |

Anything else gets `Unauthenticated` or `PermissionDenied`. A revoked session
gets `Unauthenticated` with the reason it ended (section 5.8).

The Workflow check uses the session key. The tunnel address only locates
the key; WireGuard already guarantees that one address maps to one key, and the
server records the address in the session for logs. `AgentId`
remains as a consistency check and for the existing indexes.

### 5.10 Discovery and enrollment

Discovery creates identities, and enrollment creates work. Both trust the first
caller, and both run in `Register`.

**Auto discovery** creates Hardware from an unknown Agent's reported attributes,
as `Discover` does today, and marks it as discovered. That Hardware has no
`spec.agent.authentication`, so its Agent authenticates by first use until an
operator pins a credential. A caller can have discovery create Hardware for an
`agent_id` before the operator adds it, so an operator should check for
discovered Hardware with the same `agentID` first. Under the `pinned` policy,
discovery doesn't run (section 5.7).

**Auto enrollment.**

Today, when an Agent has no Workflows at all, `GetAction` matches its reported
attributes against WorkflowRuleSets and creates an `enrollment-<agentID>`
Workflow, with or without Hardware
([enrollment.go](../../../tink/server/internal/grpc/enrollment.go)). Enrollment
supports only single-Agent templates.

With this design:

- Enrollment runs in `Register` instead of `GetAction`, under the same trigger.
  The Hardware's `spec.auto.enrollmentEnabled` still applies.
- An Agent without Hardware gets an identity first: enrollment creates a
  minimal Hardware with its `agentID` and reported attributes, marked like
  discovered Hardware, so every Agent a Workflow names has Hardware (section
  5.4).
- The created Workflow belongs to the enrolling key: its first-use binding must
  be that key (section 5.6). From then on, only that key can run the Workflow,
  so it can't be taken over. Hardware with a pinned credential must pass it before
  anything is created: an Agent with a pinned WireGuard key enrolls with its key, and a TPM
  Agent answers the challenge first, and later runs the Workflow as any key its
  TPM vouches for.
- The enrollment Workflow must not become eligible for session grants until
  ownership by the enrolling key has been recorded. Concurrent registrations
  cannot claim it during creation or initialization; performing creation and
  binding in the same RPC is not by itself sufficient to guarantee this. So for
  first use the ownership is written in the create request itself, in a
  `tinkerbell.org/enrollment-agent-key` annotation that the Workflow's first
  binding must match. Hardware with a pinned credential doesn't need it: the pin
  already decides. The Workflow has no
  Tasks until the Tink Controller renders it, so `Register` returns `WAITING`
  after creating it, and the enrolling key is granted on a later poll.

Under the `pinned` policy (section 5.7), only Hardware with a pinned credential
enrolls, after passing it. An Agent without Hardware can't enroll, because the
Hardware enrollment would create has no pinned credential.

What WireGuard can't fix: enrollment trusts the first caller. The attributes it
matches are reported by the Agent itself, so anyone who can reach the bootstrap
tunnel can fake them, match a WorkflowRuleSet, and receive that template's
Actions, including any secrets in them. That's true today too. WorkflowRuleSets
should not reference templates that carry secrets, and operators who can't
accept this should leave auto enrollment off.

### 5.11 Restarts, key changes, and rebind

**Agent restart** (crash, OOM kill, upgrade), without a reboot: the Agent reloads
its key from `/run`, so its session record still names it. Its new bootstrap
device has a new UDP source port, so the server drops the old bootstrap peer on
the first handshake from the new source (section 5.2). Then `Register`
re-issues its session, and `GetAction` re-serves the Action that was in
progress, as it already does after a server restart. The interrupted Action
runs again. Nothing opens a window for another key.

**Reboot with a pinned credential** (section 5.5): an Agent with a pinned
WireGuard key brings back the same key, and a TPM Agent a new key that its TPM
vouches for. Either way `Register` authenticates its credential and re-issues
the session, moving the record to a TPM Agent's new key and revoking the old
session key, so this works like an Agent restart, after the reboot.

**New key in the middle of a Workflow** (a reboot with first use, or a
pinned WireGuard key that was replaced): the Workflow is never handed to
another key automatically.
`Register` from the new key returns `PermissionDenied`, and the server counts
and logs the refusal with the Agent ID, the new key, and its UDP source address.
The Agent also logs its public key at startup and with every refusal. Left
alone, the Workflow ends at its timeout.

To continue it, an operator hands the Agent over to the new key:

- **First use:** rebind it with an annotation on the Workflow.

  ```yaml
  metadata:
    annotations:
      tinkerbell.org/agent-rebind: "<agent ID>=<new bootstrap key, base64>"
  ```

  The Tink Server's Workflow event handler (section 5.8) moves that Agent's
  session record in this Workflow to the new key and removes its session key,
  so the old key loses its session at once. Then it removes the annotation and
  logs the rebind. An empty key (`"<agent ID>="`) clears the record's bound key
  and removes its session key without naming a new key, so the next key to
  `Register` is bound. Bindings exist only in active Workflows, so the Workflow
  is where a rebind belongs, and no Hardware watcher is needed. The annotation
  applies only to first use: for an Agent with a pinned credential, and under the
  `pinned` policy (section 5.7), it is logged, removed, and otherwise ignored.
- **Pinned credential:** change `spec.agent.authentication` on its Hardware. It takes
  effect at the next `Register` that passes it: the credential authenticates the
  caller, the session record moves to its key, and the old session key is
  revoked when the record changes. A TPM Agent needs this only when its TPM is
  replaced.

The named key's next `Register` gets a new session, and `GetAction` re-serves the
interrupted Action. Because the operator names one key, no race opens.

**Evicting an attacker.** The same rebind is the response when an attacker won
the first session: rebind to the real Agent's key, which the Agent logs and the
server logs with the refusal. The other key loses its session and can't be
granted again while the session record names the real key. Banning the key
itself would add little, because keys are free.

**Visibility.** Refusals are not recorded on API objects. Keys are free, so an
attacker who presented a new key on every poll would otherwise force one status
write per key. Instead:

- The server logs each refused key, with the Agent ID, its UDP source, and the
  key the Agent accepts, at V(2).
- It counts authentication failures in
  `tink_server_agent_authentication_failures_total{type, trust, reason}`, where
  `reason` is one of `wireguard_key` (not the pinned key), `tpm_ek` (evidence
  missing or naming another EK), `tpm_challenge` (a wrong answer), `bound_key`,
  `enrollment_key`, `source_check`, or `not_pinned` (section 5.7). The
  labels are fixed sets, so the metric's cardinality is too. A rise means an
  attempted takeover, or an Agent that lost its key and needs a rebind.
- It counts authorization denials separately, in
  `tink_server_agent_authorization_denials_total{reason}`: a grant past the
  execution deadline, a session request for another Workflow or for a Task not
  assigned to the Agent, or a request on an ended session. `WAITING` isn't a
  denial: an Agent with nothing to run isn't counted.

None of this stops a Workflow; it reports.

If the final Action reboots the machine before reporting, the session's key lives
until the Workflow times out, but it existed only in the old boot's Agent
process.

### 5.12 Agent lifecycle

1. CaptainOS boots. `tink-agent-setup` reads the `tinkerbell_wg_*` parameters
   and passes them to the Agent.
2. The Agent loads its key (a pinned key, or the one left in `/run` by an
   earlier run) or generates one, and brings up the bootstrap tunnel. If it
   finds a TPM, it creates its EK and attestation key and logs the EK hash
   (section 5.5).
3. It polls `Register`. Typical results are `NotFound` (unknown Agent),
   `WAITING` (nothing to run yet), `CHALLENGE` (answered on the next poll), and
   `GRANTED`.
4. On `GRANTED` it brings up a session device with the issued key and runs
   its Tasks over it with `GetAction` and `ReportActionStatus`, as today.
5. It keeps the session and polls `GetAction` on it, without calling
   `Register` (section 5.8). When requests on the session fail, because the
   server revoked the key or the tunnel broke, it tears the session device down,
   logs why the session ended, and goes back to step 3.

The Agent never says goodbye. Its bootstrap peer expires, and its binding and
sessions end with its Workflow.

### 5.13 Server keys

The operator provides the server keys, typically as a Secret mounted into the
Tinkerbell pod as files. The server reads them at startup; it neither creates
nor reads Secrets through the API, so it needs no new RBAC. Every replica
mounts the same files, which keeps their devices and pre-shared key derivation
in step.

| Key | Flag | Value |
|---|---|---|
| Bootstrap device private key | `--wireguard-bootstrap-key-file` | `wg genkey` |
| Session device private key | `--wireguard-session-key-file` | `wg genkey`, different from the bootstrap key |
| PSK root | `--wireguard-psk-root-file` | 32 random bytes, base64: `openssl rand -base64 32` |
| Tunnel prefix | `--wireguard-prefix` | A random ULA `/48`, not a secret |

With WireGuard enabled, a missing flag or an unreadable or malformed key fails
startup and names what is missing.

The PSK root also keys the `Register` challenge tickets (section 5.3), through a
key derived from it with its own label, so that no ticket key can equal a
pre-shared key.

### 5.14 Key rotation

Rotation follows [headscale](https://github.com/juanfont/headscale), which keeps
its server key in a file and rotates it by replacing the file and restarting,
with no slots or rotation state. That works for headscale because its clients
don't pin the server key: they fetch it over TLS from `/key`. Here, Agents learn
the bootstrap key from the boot parameters Smee writes on every boot, and the
session key and PSK root from `Register`. So:

- **Keys are files, and rotating one means replacing its file and restarting.**
  The server keeps no rotation state and tracks no deadlines; the operator
  decides when an overlap ends.
- **Session key and PSK root: no overlap.** Agents only ever learn these through
  `Register`. After a restart with a new session key or PSK root, an Agent's
  session stops working: its handshake goes to a key the server no longer has,
  or uses a pre-shared key the server no longer derives, and nothing answers.
  The Agent bounds each call through the session tunnel (15 seconds, a few
  WireGuard handshake retries), then returns to `Register`. Its binding is still
  in the Workflow's status, so it gets a re-issued session on the new key. A
  running Action carries on; its report goes over the new session. A new PSK
  root also voids outstanding challenge tickets; their Agents get a new
  challenge on the next poll.
- **Bootstrap key: an optional previous key that only redirects.** New boots
  learn the new key from Smee. Agents already running know only the old key and
  port. During a rotation the server can run a second bootstrap device with the
  old key on the old port (`--wireguard-previous-bootstrap-key-file`,
  `--wireguard-previous-bootstrap-port-v4` and `-v6`). It answers every `Register` with
  `WAITING` and `move_to`: the current key and endpoint. It grants nothing and
  creates nothing. `move_to` arrives over the old tunnel, which is
  authenticated, so the Agent trusts it. The Agent switches, keeping its own
  key, and saves the new server in `/run/tink-agent/wireguard-server.json`, so an
  Agent restart doesn't fall back to the old key; `/run` is a tmpfs, so a reboot
  uses fresh boot parameters.
- **A WireGuard device has exactly one key**, so the old key keeps the old port
  and the new key takes another. Bootstrap ports alternate between two values
  across rotations.

Rotating the bootstrap key:

1. Generate a new key. Configure it as the bootstrap key on a different port,
   and the old key and port as the previous bootstrap key.
2. Restart. Smee advertises the new key and port from then on.
3. After running Agents have polled, a few minutes, remove the previous bootstrap
   key and restart again.

Without the previous key, Agents booted with the old key that are idle or
waiting can't register until they reboot. Agents already in a session finish
their Workflow, unless the session key rotated too.

With several replicas, a rolling restart briefly leaves replicas with different
keys, so some Agents re-register more than once. It settles once every replica
runs the new keys. Restarting them together avoids the churn.

Rotating the prefix changes every tunnel address, so it is a bootstrap key
rotation that also needs new boot parameters: Agents that were redirected keep
the old prefix. Change it only with a reboot of the affected machines.

### 5.15 Modes

`--wireguard-mode`:

| Mode | Plain gRPC | Tunnels | Authorization |
|---|---|---|---|
| `disabled` (default) | Yes | No | None, as today |
| `optional` | Yes, for Agents without a pinned credential or a binding | Yes | Enforced in the tunnels, and on the plain path for Agents with one |
| `required` | No; gRPC only in the tunnels | Yes | Enforced |

`optional` lets CaptainOS images move over one at a time. In `optional` mode the
plain listener refuses requests for an `agent_id` that has a pinned credential or a
binding. An Agent without a pinned credential is bound only while a Workflow has
work for it (section 5.6). Between Workflows, and when its next Workflow appears
until it registers, anyone can still use its `agent_id` on the plain path, as
today, and nothing reports it. Only `required` closes the plain path, so
`optional` is for migration, not a resting state.

API additions: Hardware `spec.agent.authentication`, with
`spec.agent.attestation` reserved (section 12); Workflow

`tinkerbell.org/agent-rebind` and `tinkerbell.org/enrollment-agent-key`. There
are no new conditions, and Hardware gets no status field: bindings live in the
session records.

Helm requires, when WireGuard is enabled, the name of an existing Secret holding
`bootstrap.key`, `session.key`, and `psk-root`, and the prefix. It mounts the
Secret read-only as files, points the key file flags at them, and exposes both
UDP ports on the Tinkerbell Service. As for the other services, the IPv6 ports
default to the IPv4 ones and must equal them when the Service serves both

Agent: the three flags in section 5.2, `-wireguard-key-file`, and `-tpm`
(default `true`: use the TPM, when there is one, for `tpm` evidence). CaptainOS's
`tink-agent-setup` will need to handle these new Agent flags, passing them
`-wireguard-key-file=/run/tink-agent/wireguard.key`. A TPM credential needs nothing else
from CaptainOS: the Agent talks to `/dev/tpmrm0`, which the kernel's built-in
TPM drivers provide.

## 6. Security

The attacker sits on the provisioning network. They can sniff traffic, spoof MAC
and IP addresses, fetch iPXE scripts, and send anything to Tinkerbell's ports.
They can't compromise the Tinkerbell control plane or the Kubernetes API.

**Transport and boot**

| Attack | Today | With this design |
|---|---|---|
| Read Actions and their secrets in transit | Possible without TLS | Encrypted |
| Flood the bootstrap device | n/a | Cookies and per-IP handshake rate limiting mitigate floods. Every bootstrap peer has a fixed maximum lifetime; missing or rejected registrations trigger earlier removal (section 5.2). Running Workflows use a separate session device, but sustained floods can still exhaust bootstrap capacity or shared server resources. |
| Change the iPXE script to swap the server key | Can already swap the kernel and initramfs | Unchanged. HTTPS iPXE is the mitigation for both. The boot path is the trust anchor for the bootstrap key, as TLS is for headscale's `/key`. |
| Redirect a running Agent to a fake server | n/a | No. A new bootstrap key reaches a running Agent only as `move_to`, over the old tunnel, which is authenticated (section 5.14). |

**Authentication**

| Attack | Today | With this design |
|---|---|---|
| Pose as another Agent | Succeeds | Only as its bound key, or as a key its pinned credential authenticates |
| Pose as an Agent with a pinned credential | Succeeds | No. For a pinned WireGuard key, only that key is accepted; for a TPM, only a key the pinned TPM vouches for. There is no binding to race for. |
| Answer a TPM challenge without the TPM | n/a | No. Only the TPM holding the pinned EK can recover the secret, and answering for another key would need code running on that machine (section 5.5). |
| Replay a TPM challenge answer | n/a | No. The ticket names the bootstrap key that asked, and expires after 30 seconds (section 5.3). |
| Win a Workflow's first session | n/a | Not for an Agent with a pinned credential, nor under `pinned`. Otherwise, for first use, only between the Workflow having work for it and the real Agent's first `Register`. With the source check on, also only from that Hardware's address. The real Agent is then refused, the failure is counted and logged, and the operator rebinds to the real key. |
| Bind an idle machine ahead of its next Workflow | n/a | No. Nothing is bound until a Workflow has work for the Agent. |
| Get an identity through discovery or enrollment | Succeeds | Still succeeds when those are enabled, but the Hardware created has no pinned credential (section 5.10). Under `pinned`, discovery is off and only Hardware with a pinned credential enrolls. |

**Authorization**

| Attack | Today | With this design |
|---|---|---|
| Fetch another Agent's Actions | Succeeds | Needs that Agent's session, which only its authenticated credential gets |
| Report false Action status | Succeeds | Needs the session, and only for the session's Workflow and the Agent's Tasks |
| Take over a running Workflow | Succeeds | No. Each Agent's record names one credential, and only an operator can move it. |
| Use a captured session key later | n/a | No. It's removed when its session ends. |
| Reach the Workflow service with any other key | Succeeds | No. The session device admits only granted keys. |
| Get a Workflow through enrollment | Succeeds | Still succeeds when enabled (section 5.10). The Workflow belongs to the caller's key, so it can't be taken from them, but nothing proves who they are. |

Residual risks, transport:

- **Bootstrap availability is not guaranteed.** A caller cannot extend a peer's
  lifetime by calling `Register` or renewing handshakes, but can continually
  reconnect with fresh keys. Retained state depends on admission rate and peer
  lifetime; sufficiently high sustained admission can still deny service.
- **An unverified handshake initiation can reset a bootstrap peer.** The server
  drops a bootstrap peer when an initiation for its key arrives from a new source
  (section 5.2), before the initiation is verified. A replayed initiation can so
  cost a real Agent one retry; it can't bind or reach anything.
- **`optional` mode leaves the plain path open** for Agents without a pinned
  credential between Workflows, and until they register for a new one (section 5.15).
- **The server key files**, and the Secret they come from, are a trust anchor.

Residual risks, authentication:

- **Trust on first use** for Agents without a pinned credential. An attacker who calls
  `Register` first after a Workflow appears gets that Workflow's session, and an
  Agent that was already waiting has no head start (section 5.6). A
  pinned credential removes this, and the `pinned` policy removes it for every
  Agent (section 5.7); otherwise the source check narrows who can bind, and
  the authentication failure metric and a rebind are the response.
- **Discovery can create Hardware first.** A caller can have discovery create
  Hardware for an `agent_id` before the operator adds it (section 5.10).
- **Authentication failures don't stop an attacker who bound first.** By design they are only
  counted and logged, so a session already issued to the wrong key stays active
  until an operator rebinds. Failing the Workflow instead would let anyone who
  knows an `AgentId` stop it. Refusals are not written to API objects, so an
  operator relies on the metric and logs to notice one.
- **Write access to Hardware decides how Agents authenticate,** through
  `spec.agent.authentication`, and write access to Workflows through the rebind
  annotation.
- **A pinned WireGuard key is trusted as set.** Nothing proves where it's kept,
  or that the key file wasn't copied off the machine.
- **A pinned EK hash is trusted as set.** It names one TPM, but that the TPM is
  in the machine the Hardware describes is only as good as the inventory the
  hash came from.
- **Reusing a bootstrap key shares its compromise blast radius.** A stolen key
  can obtain sessions for every Agent ID that authorizes it. Independently
  generated pinned keys are recommended, but global key uniqueness is not
  enforced.
Residual risks, authorization:

- **Auto enrollment trusts the first caller** and self-reported attributes
  (section 5.10). Under `pinned`, only Hardware with a pinned credential enrolls.
- **Write access to Workflows decides what Agents run,** as it does today.
- **The server knows each session private key** when it issues it. That
  doesn't weaken anything, because the server is the only party that trusts the
  key, and it doesn't store it.
- **Actions run with the Agent's access.** Privileged Actions can read the
  Agent's key file or memory, and use its TPM.

## 7. Dependencies and footprint

- `github.com/tailscale/wireguard-go` (tailscale branch) and
  `gvisor.dev/gvisor`. The proof of concept uses
  `v0.0.0-20261015173605-9d8961514fae`, which has the hybrid handshake
  (`NewPeerConfig.Hybrid`). `PeerLookupFunc` returns `(*NewPeerConfig, bool)`,
  with per-peer pre-shared key and hybrid settings.
- The fork doesn't roam: a peer's endpoint is fixed when it is created, and the
  lookup callback isn't told the source. `pkg/wireguard` wraps the UDP bind to
  learn it through `conn.InitiationAwareEndpoint` and passes it in
  `NewPeerConfig.Endpoint` (section 5.2).
- `github.com/google/go-tpm` for TPM credentials (section 5.5): the Agent's TPM commands
  through `/dev/tpmrm0`, and the server's `TPM2_MakeCredential`, which runs in
  software (`tpm2.CreateCredential`). Pure Go, so no cgo and no `tpm2-tss`.
- No `tailscale.com` and no DERP relay.
- The Agent binary grows. Measure it before CaptainOS ships it.
- Agents need direct UDP to the server. There's no NAT traversal beyond the
  Agent initiating and keeping the mapping alive.

## 8. Operations

- **Replicas.** Bindings and sessions are in the API, every replica mounts the
  same key files, and pre-shared keys are derived. Challenge tickets carry their
  own state, so a challenge and its answer may reach different replicas. So any
  replica can serve any Agent, if the load balancer keeps each Agent's UDP flow
  on one replica. Every
  replica watches Workflows to remove ended keys.
- **API writes.** Idle Agents cost none. Sessions, and the bindings in them, cost
  one Workflow status write per Agent per Workflow, plus one per re-issue.
  Refused keys cost none (section 5.11).
- **MTU.** The tunnel MTU is 1420. Underlay networks with less than 1500 bytes
  need a lower value.
- **Logs.** Idle Agents poll every few seconds, so routine `Register` answers
  (`WAITING`, unknown Agent, deadline passed) are logged only at V(1), refused
  keys at V(2), and only server and backend failures and session grants by
  default. Polling less often when idle would cut logs and load, but lengthen
  the first-use window (section 5.6).
- **Metrics.** Authentication failures by credential type, trust, and reason, and authorization
  denials by reason (section 5.11). Still to add: peers per
  device, bootstrap peers removed by reason (maximum lifetime, no `Register`,
  rejected registration, moved source), bindings, sessions issued and removed,
  rebinds, and authorization denials by request.

## 9. Alternatives considered

- **One device for both layers,** with the interceptor alone keeping bootstrap
  keys away from the Workflow service. Fewer ports, but a bug in one check would
  expose Workflows, and a flood of bootstrap handshakes would share a device
  with running Workflows.
- **The Agent's bootstrap key as its only key.** No server-issued key, so no
  per-Workflow credential that dies with the Workflow.
- **The Agent generates its session key** and sends the public half. No
  stronger, because the server is the only party that trusts the key, and it
  adds a key exchange step.
- **Idle bindings:** bind an Agent to its Hardware before a Workflow exists,
  with a lease the Agent renews. Rejected. An attacker could bind a powered-off
  or idle machine ahead of its next Workflow. It needs a lease, renewals, and a
  Hardware status write per idle Agent; a reboot waits for the lease; and a
  release call can't cover a BMC hard power-off. It only helps an Agent that is
  already waiting when its Workflow appears, and a pinned credential covers
  that.
- **Smee netboot ends a binding.** Rejected: any machine on the network can make
  a netboot request, so this would let anyone reopen the binding window.
- **Hand a Workflow over to a new key automatically** after a reboot. Rejected:
  whoever registered first after the reboot would get the rest of the Workflow.
- **A policy ConfigMap** for pinned keys and a deny list. Rejected: pinned keys
  belong with the Workflow they authorize, and a deny list adds little, because
  keys are free and addresses can change. Rebinding evicts a key.
- **A Workflow handover annotation.** Not needed: rebinding or editing a pinned
  credential moves the session.
- **The device performs WireGuard's private key operations,** so the key never
  leaves it. wireguard-go uses the static private key in about four places: once
  per peer, then on every handshake. A patch could delegate those to a device,
  but Tinkerbell would carry it on top of Tailscale's fork. That is what a
  "wireguard-go plus tpm2-tss" design needs: the static key is used for X25519
  Diffie-Hellman on every handshake, not for signing, so the TPM would have to
  perform X25519 ECDH (`TPM2_ECDH_ZGen`). Recent TCG specifications add
  Curve25519 (`TPM_ECC_CURVE_25519`), but shipping TPMs implement only NIST
  curves, as do most HSMs (YubiHSM 2, for example); YubiKey 5.7+ PIV and a few
  PKCS#11 HSMs do support it. Not pursued: a TPM credential authenticates by the TPM
  without the TPM holding the WireGuard key.
- **A key derived deterministically by the device:** an HMAC, under a key that
  never leaves the TPM, HSM, or security key, of a fixed label, turned into an
  X25519 key. It needs no stored blob and works with any HMAC-capable device,
  but the derived key is in the Agent's memory like a sealed key. Not pursued.
- **The device signs each boot's WireGuard key** at `Register`, against a
  device public key the Hardware lists. This is what a TPM credential does, with
  credential activation and the tunnel binding the key instead of a signature
  (section 5.5). For HSMs and security keys it isn't pursued.
- **A WireGuard key sealed to the TPM,** pinned as a WireGuard key: an earlier
  version of this design. The TPM protects the key at rest, but the key needs
  onboarding into the Hardware, a CaptainOS unit to unseal it, and a PCR policy
  to keep Actions from unsealing it again; sealing to PCRs also breaks when the
  boot chain changes. A TPM credential needs none of these, and nothing is stored.
- **Identity on Workflows** for Agents without Hardware (`spec.agentAuthentication`
  on the Workflow): an earlier version of this design. Rejected: an
  authorization object then decides identity, which needed precedence rules
  ("the Hardware always wins") and an exception for discovered Hardware. Every
  Agent has Hardware instead (section 5.4).
- **A separate identity object** (for example `Agent`) for Agents without
  Hardware. Rejected: a new configuration object, when Hardware with only an
  `agentID` already serves.
- **A streaming `Register`** for the TPM challenge, as SPIRE's `AttestAgent`
  does. Rejected: Tinkerbell has no streaming RPCs, and adding the first one for
  a single round trip adds complexity when Tinkerbell runs in Kubernetes. The
  polling loop already carries the round trip (section 5.3).
- **A separate `Challenge` RPC.** The same stateless ticket, with one more method
  and no benefit over a `CHALLENGE` state.
- **Validating EK certificates against TPM manufacturer CAs** instead of pinning
  EK hashes. A valid certificate proves a TPM is genuine, not which machine it's
  in, so a pinned hash is needed anyway. Possible as an addition (section 12).
- **Answering only pinned keys at the bootstrap device** under the `pinned`
  policy, so unknown keys get no handshake. Rejected: a TPM Agent's key is new
  every boot. A second bootstrap device just for pinned WireGuard keys could keep it,
  at the cost of another port.
- **Tinkerbell delivers each Agent's key** on the kernel command line, in a
  per-host initramfs, or on BMC virtual media. Each delivery path is weaker than
  a key generated on the machine, or works only with virtual-media boot.
- **tailcat.** The same WireGuard model plus NAT traversal, but it needs a DERP
  relay, pulls in `tailscale.com`, has no API or wire stability promise, and its
  threat model doesn't yet cover hostile peers.
- **mTLS.** Not pursued.
- **Conditions on the Workflow and Hardware for refused keys** (`AgentKeyChanged`,
  `AgentKeyConflict`). Rejected: keys are free, so an attacker presenting a new
  key on every poll would force a status write per key. Refusals are counted and
  logged instead (section 5.11).
- **The server generates its keys and stores them in a Secret on first start.**
  Rejected: it needs RBAC to create and update Secrets. The operator provides
  the keys as files instead (section 5.13).
- **The rebind annotation on the Hardware.** Rejected: applying it needs a
  Hardware watcher. Bindings live in active Workflows, so the annotation goes on
  the Workflow, where the existing Workflow event handler applies it (section 5.11).
- **Syslog through the session tunnel**, attributed by key. Left out of the
  initial design.
- **Key slots with rotation states** (`active`, `retiring`) and a migration
  deadline tracked by the server. Rejected: replacing key files and restarting,
  as headscale does, with an optional previous bootstrap key, does the same with
  no state (section 5.14).
- **Fetching the bootstrap key at runtime,** as Tailscale clients fetch
  headscale's `/key`: Smee serves the current key, and an Agent re-fetches it
  when handshakes fail. Rejected over plain HTTP: a network attacker could block
  the Agent's UDP, then answer the fetch with their own server's key, at any
  time rather than only at boot, and a fake server can hand the Agent Actions.
  Acceptable only over verified TLS. The authenticated redirect covers running
  Agents instead.
- **Generating missing server keys on first start,** as headscale does. Not
  pursued: in Kubernetes the keys come from a read-only Secret mount. It could
  help installs without Kubernetes, as an explicit opt-in.

## 10. Implementation phases

1. **`pkg/wireguard`.** Move to the current fork API. Remove the hardcoded
   addresses, paths, ports and DNS. Add address derivation, the hybrid
   handshake, the UDP bind wrapper that learns initiation sources, and tests.
2. **Server devices.** Both tiers, the key file flags and validation, admission
   callbacks, bootstrap peer lifetimes and moved-source removal, the shared
   device component in `cmd/tinkerbell`, flags, and `optional` mode. A tunnel
   gRPC server without TLS next to the plain one.
3. **Bindings and `Register`.** First-session binding in Workflow status, an
   index of session records by Agent (rebinds and the plain-path guard need
   every active Workflow with a record for an Agent, not only those where it is
   the current Agent), the source check, discovery moved into `Register`, and
   the rebind annotation on the Workflow.
4. **Sessions and pinned keys.** Hardware `spec.agent.authentication` with
   pinned WireGuard keys, per-Agent records with a `credential` and a `session`, a
   key index, key issuance, derived
   pre-shared keys, the session admission callback, revocation with a grace
   period and reasons, the interceptor, and the authentication and authorization
   metrics. Establish the
   Workflow execution clock atomically with its first session grant, and enforce
   the fixed deadline in the Tink Controller, in `PENDING` and `RUNNING`, and in
   session authorization.
5. **TPM credentials.** `tpm` evidence and the `CHALLENGE` state in
   `Register`, stateless tickets, `TPM2_MakeCredential` on the server, the
   Agent's EK and attestation key, `TPM2_ActivateCredential`, and the EK hash in
   the Agent's startup log.
6. **Enrollment.** Move it into `Register`, record the enrolling key in the
   create request, and grant the created Workflow's session to that key.
7. **Agent.** Key file, bootstrap and session tunnels, the `Register` loop,
   session switching, and logging why a session ended. Measure binary size.
8. **CaptainOS and Smee.** Kernel parameters, `tink-agent-setup` handling the
   new Agent flags, Helm values and ports.
9. **Key rotation.** The previous bootstrap key's redirect, the Agent's saved
   server, and bounded calls through the session tunnel.
10. **`required` mode,** the `pinned` policy, docs, and end-to-end tests: boot an
    Agent, bind, run a Workflow with a second, administrative Agent that has
    Hardware with only an `agentID`, restart the Agent mid-Action, reboot a
    pinned WireGuard Agent and a TPM Agent mid-Workflow, rebind to a new key, enroll
    an Agent without Hardware, rotate each server key while Agents are idle and
    mid-Workflow, check that other and ended keys are refused, that a TPM
    Agent with another EK or a wrong answer is refused, and that under the
    `pinned` policy Agents without a pinned credential are refused.

## 11. Decisions

| Question | Decision |
|---|---|
| Explicit `Register` RPC, or bind on the first `GetAction`? | Explicit `Register` |
| What is an Agent's tie to its key called? | A binding |
| Where do bindings and sessions live? | Both in Workflow status: the binding is the session record's bootstrap key |
| Must a bootstrap key be unique across Agent IDs? | No. Each Agent is authorized independently, and each operational session is scoped to one Agent in one Workflow. Separate machine keys are recommended to limit compromise blast radius. |
| Bindings outside a Workflow? | No. An Agent is bound only while a Workflow has work for it (section 5.6). |
| How does an Agent prove who it is? | With a credential, described by its type, a WireGuard key or a TPM, and its trust, first use or pinned (section 5.5) |
| Why type and trust, not a single method? | First use and a pinned key are both WireGuard keys, and every Agent proves one. The type says what identifies the Agent, and the trust says why it was accepted; a TPM trusted on first use becomes expressible. |
| What is the field called? | `spec.agent.authentication`, on Hardware. `agentID` already names the Agent; this says how it proves it. `spec.agent.attestation` is reserved, and `agentID` stays at `spec.agentID` for now. |
| Is a TPM credential authentication or attestation? | Authentication: it establishes which TPM, and so which Agent, is calling. Attestation, appraising a machine's state, is out of scope, with `spec.agent.attestation` reserved for it (section 5.5). |
| Are authentication and authorization separate? | Yes. Authentication verifies the Agent's credential against its Hardware; authorization decides from the Workflow and issues a session. First use is the one deliberate coupling (section 5.6). |
| Where does an Agent's identity live? | Always in a Hardware object, including administrative Agents, which get Hardware with only an `agentID`. Workflows only authorize. |
| Workflows with Tasks for several Agents? | One session per Agent per Workflow |
| When does the Workflow execution timeout start? | At the first operational session grant, atomically with its session record. All sessions expire at the same fixed Workflow deadline; re-issuance and rebinds do not extend it. |
| New configuration objects (policy ConfigMap)? | None |
| Auto enrollment? | Moves into `Register`. An Agent without Hardware gets a minimal Hardware first; the Workflow belongs to the enrolling key. |
| Can a Smee netboot end a binding? | No. It would reopen the window for anyone on the network. A binding ends with its Workflow (section 5.6). |
| Hybrid post-quantum handshake? | On, for both devices |
| Multiple server keys? | One key per tier, plus an optional previous bootstrap key during a rotation (section 5.14). |
| How are server keys rotated? | Replace the key file and restart, as headscale does. No rotation state. |
| Overlap when rotating the session key or PSK root? | None. Agents re-register and get re-issued sessions. |
| Overlap when rotating the bootstrap key? | Optional: the previous key's device redirects running Agents with `move_to`. |
| Where do the server keys come from? | The operator, as files, typically a mounted Secret. No Secret access through the API (section 5.13). |
| HookOS? | Deprecated. CaptainOS only. |
| Syslog through the tunnel? | No. Not in the initial design. |
| Tootles through the tunnel? | No. Its clients are installed OSes, which have no tunnel. |
| Record refused keys on the Workflow or Hardware? | No. A V(2) log line and a metric (section 5.11). |
| Fail the Workflow when a key is refused? | No. Refusals are only reported. |
| Where does a rebind go? | An annotation on the Workflow, applied by the Workflow event handler. No Hardware watcher. |
| Cancel the running Action at the execution deadline? | No. An Action ends at its own timeout; its report is dropped and the reason logged (section 5.8). |
| Workflow without a `global_timeout`? | A default of one hour. |
| Agent restart in the middle of a Workflow? | Continues automatically: the key is kept in `/run` |
| Machines with a TPM? | A TPM credential: the Hardware pins the EK hash. The WireGuard key stays new every boot and nothing is stored. No first-session race, and reboots continue automatically. |
| How is the WireGuard key tied to the TPM? | By the tunnel: the challenge and answer travel through the key's own bootstrap tunnel, and the ticket names the key. No quote or signature. |
| EK hash format? | SHA-256 of the EK's PKIX DER, lowercase hex: spire-tpm-plugin's `pub_hash` |
| EK certificates? | Sent, not validated. The pinned hash decides (section 12). |
| Which credentials need a challenge? | Only those whose type isn't the tunnel key: TPM today. The WireGuard handshake already proves a WireGuard key, first use or pinned (section 5.3). |
| How does the TPM challenge fit `Register`? | A `CHALLENGE` state with a stateless, encrypted ticket, answered on the next poll. No streaming RPC and no server state. |
| Boot integrity (PCRs)? | Out of scope. This design authenticates. |
| Machines with persistent storage but no TPM? | A pinned WireGuard key in the Hardware. |
| Agent release call? | None. Bindings end with their Workflow or by rebind; there is nothing to release between Workflows. |
| New key in the middle of a Workflow? | Automatic only for a TPM, which is the identity. For WireGuard keys, first use or pinned, never: an operator rebinds or edits the pinned key. |
| Source IP check? | Optional, off by default |
| Require a credential an operator set? | Optional: `--agent-authentication-policy=pinned`, which requires `required` mode. `Register` enforces it; the bootstrap device still answers every key, because `tpm` keys can't be known ahead of time. Discovery is off and the rebind annotation is ignored under it (section 5.7). |
| Deny list? | No. Rebinding evicts a key. |

## 12. Future work

- **Manual approval.** A binding stays pending until an operator approves it,
  like kubelet CSR approval. Removes trust on first use at the cost of a manual
  step per Workflow.
- **One-time enrollment token.** Smee puts a single-use random value in the
  kernel parameters for each boot, and `Register` must present it to bind.
  Narrows the window to whoever fetched that boot's script.
- **SPIFFE identities.** A SPIFFE credential type, `spec.agent.authentication.spiffe.id:
  spiffe://<trust domain>/...`. A SPIRE agent on the machine attests it, for
  example with spire-tpm-plugin, whose `tpm:pub_hash` selector is the same hash
  as a TPM credential's. tink-agent gets an X.509-SVID from the SPIRE Workload API, sends
  it as `spiffe` evidence, and signs the challenge with its key: proof of
  possession, bound to the tunnel like a TPM credential. The server checks the SVID against
  the trust domain's bundle. It fits the existing evidence, challenge,
  credential union, and refusal reasons, with no new shape. Since every Agent has
  Hardware, Tinkerbell can name Agents `spiffe://<trust domain>/tinkerbell/hardware/<namespace>/<name>`. JWT-SVIDs are bearer tokens, so
  X.509-SVIDs are preferred.
- **Attestation,** in `spec.agent.attestation`, reserved for it. It would hold
  appraisal policy: trusted TPM manufacturer CAs for the EK certificate the
  Agent already sends, or a reference to them; an expected platform certificate
  serial; and required PCR values or a reference to a measured-boot policy.
  Appraisal results, with when they were made, belong in Hardware status, not
  spec. They would feed authorization, as a third input next to the credential
  and the Workflow (section 5.8): for example, run a Workflow only on a machine
  whose attestation passed in this boot. Authentication doesn't change.
- **EK certificate validation,** the first piece of attestation: check the
  certificate the Agent already sends against TPM manufacturer CAs, and
  optionally pin its serial, as Keylime and Teleport do.
- **EK hashes at scale.** Import them from OEM platform certificates (Dell SCV,
  HPE), which bind the TPM to the server's serial number, or read them through
  the BMC with Rufio.
- **A TPM trusted on first use,** `tpm: {}` in the Hardware: the first TPM to
  answer a challenge for the Agent, within an enrollment window the Hardware
  sets, is pinned, once for the machine rather than per Workflow. The credential
  type and trust already express it; it needs the window, and a decision on who
  writes the pin.
- **ECC endorsement keys,** for TPMs without an RSA EK certificate.
