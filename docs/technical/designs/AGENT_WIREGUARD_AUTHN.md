# Agent Authentication with WireGuard

Status: proposed

## 1. Problem

Nothing authenticates the Tink Agent to the Tink Server.

- The Agent names itself. Every `GetAction` and `ReportActionStatus` carries an
  `AgentId`, which comes from `worker_id` on the kernel command line. The server
  believes it ([grpc.go](../../../tink/server/internal/grpc/grpc.go)). Anyone who
  can reach the gRPC port can pose as any Agent: they can fetch its Actions,
  including any secrets in Action environment variables, and report false results.
- TLS is optional and authenticates only the server
  ([transport/grpc](../../../tink/agent/internal/transport/grpc/grpc.go)). Without
  it, Actions and their secrets cross the network in plaintext.
- Auto discovery and auto enrollment create Hardware and Workflows for whatever
  `AgentId` asks, so a caller can also create objects.
- Smee's syslog receiver identifies the sender by source IP, which anyone on the
  provisioning network can spoof.

## 2. Goals

- Authenticate the Agent cryptographically, then authorize each request against
  the Agent's identity and the Workflow it is for.
- A credential that can read or change a Workflow exists only while that
  Workflow has work for the Agent.
- Encrypt all Agent to Tinkerbell traffic: gRPC and syslog.
- No certificate authority, no certificates to issue or expire, no new external
  service, and no new configuration objects.
- No root, kernel module, or host network changes on the Agent or the server.
- Make takeover attempts visible, and give operators a way to respond.
- Work on machines without a TPM or other persistent key, with no per-boot or
  per-Workflow human step, so it scales to any fleet. There, first contact is
  still trust on first use, as it is today; the design narrows that window and
  makes takeover attempts visible, a modest improvement in security posture.
- Provide a path to persistent, TPM-backed keys, which authenticate every connection,
  including the first.
- Enable it gradually: off, optional, then required.

## 3. Non-goals

- Smee's boot path (DHCP, TFTP, iPXE, ISO). Firmware can't run WireGuard.
- The installed OS.
- Tootles. Its clients are the installed OS (cloud-init), which has no tunnel,
  so it keeps its plain listener and source IP lookup in every mode.
- The UI and the Kubernetes API, which keep Kubernetes authentication and RBAC.
- The NATS and file transports.
- HookOS, which is deprecated. CaptainOS is the only OSIE this design targets.
- Continuing a Workflow on a new key automatically.
- Proving the attributes an Agent reports (section 5.6).
- mTLS.
- Proving that a persistent key is held by a TPM (attestation). The design leaves
  room for it (section 12).

## 4. Overview

Two layers of WireGuard identity, each with its own server device:

| | Bootstrap | Session |
|---|---|---|
| Agent key pair | Generated by the Agent, or a persistent key pair. The private key stays on the machine. | Generated by the server for one Agent in one Workflow. The private key is sent once over the bootstrap tunnel and not stored. |
| What the server keeps | The public key: in a binding, or set as a persistent key | The public key, in the session record |
| Lifetime | One boot, or as long as the persistent key | While the Workflow has work for that Agent |
| Tied to its Agent by | A **binding**: the public key a Workflow's session record names, from the first session until the Workflow ends. Or a **persistent key**: a public key set on the Hardware or Workflow | A **session** in Workflow status |
| Server admits | Any public key, just in time; retained only for a bounded lifetime, with earlier removal for missing or rejected `Register` calls | Only public keys with an active session |
| Reaches | `Register` | `GetAction`, `ReportActionStatus`, syslog |

```text
  Smee (iPXE script / ISO kernel cmdline)
    │  all public: bootstrap server public key, UDP endpoint, tunnel prefix
    ▼
  Agent ── loads or generates its bootstrap key pair
    │        private key: never leaves the machine
    │        public key:  what the server sees, binds, or matches
    │
    │  UDP, WireGuard: bootstrap device
    │  (the handshake proves the Agent holds the private key)
    ▼
  Register(agent_id) ──► Workflow work for this Agent?
    │                      └──► caller's public key is the persistent key, the
    │                           bound key, or the first to ask? yes: session
    │
    │  ◄── session private key, PSK, session server public key
    │        (the server generates the session key pair, returns the private
    │         key once, and keeps only the public key in Workflow status)
    │
    │  UDP, WireGuard: session device
    │  (admits only session public keys with an active session)
    ▼
  GetAction / ReportActionStatus / syslog
    │  interceptor: source address → session public key → session → Workflow, Agent
    ▼
  Agent's work done ──► session public key removed from the device,
                         Agent drops the session private key, back to Register
```

WireGuard's cryptokey routing does the authentication: each Agent public key is
admitted with only its own `/128`, and only the holder of the matching private
key can complete a handshake as that key. WireGuard drops any packet from that
key with a different source address. The source address the server sees is
therefore an authenticated key identity. For `Register`, the server checks that
key against the binding or persistent key for the requested Agent and Workflow.
For session requests, it maps the key to one Workflow and Agent.

An Agent is bound only while a Workflow has work for it. An idle Agent holds
nothing, so there is no lease to renew or expire, and nothing for an attacker to
take ahead of time.

The building blocks exist on the `secrets` branch: `pkg/wireguard`, a userspace
device built on Tailscale's
[wireguard-go fork](https://github.com/tailscale/wireguard-go) and gVisor's
netstack, a gRPC listener inside the tunnel, and an Agent dialer through it.

## 5. Design

### 5.1 Server devices

The WireGuard devices belong to the `tinkerbell` binary, not to one service, so
the Tink Server and Smee's syslog receiver can both listen inside them.

- Two userspace devices: bootstrap and session. Each has its own private
  key and UDP port, because a wireguard-go device has exactly one private key.
- Keys live in a Secret, generated on first start (section 5.12).
- One generated ULA `/48`. The bootstrap tunnel uses its first `/64`, the
  session tunnel the second. The server is `::1` in each. The prefix exists
  only inside gVisor's netstack, so it can't conflict with host or provisioning
  networks.
- Services inside the tunnels:

| Service | Bootstrap device | Session device |
|---|---|---|
| gRPC `:42113` | `AgentService` (`Register`) | `WorkflowService` (`GetAction`, `ReportActionStatus`) |
| Syslog `:514/udp` | No | Yes |

- The hybrid post-quantum handshake is on for both devices. Both peers must
  agree and there is no fallback, so the Agent always enables it too. The fork
  supports it for lazily created peers (`NewPeerConfig.Hybrid`) and through the
  configuration protocol (`hybrid=true`).

### 5.2 Bootstrap tunnel

The Agent's side:

- The Agent loads its bootstrap private key from `-wireguard-key-file`. If the
  file doesn't exist, it generates an X25519 key and writes it there with mode
  `0600`. It logs the public key at startup. The private key never leaves the
  machine.
- CaptainOS uses `/run/tink-agent/wireguard.key`. `/run` is a tmpfs, so the key
  survives an Agent restart (section 5.8) but not a reboot: each boot gets a new
  key, unless the Agent has a persistent key (section 5.5).
- Its bootstrap address is `bootstrap prefix || first 64 bits of SHA-256(public
  key)`. Both sides compute it, so there is no address allocation state.
- It sets a persistent keepalive (25s) so NAT mappings stay open.

Smee writes three public values to the kernel command line, the same way it
writes `grpc_authority` today, and CaptainOS's `tink-agent-setup` passes them to
the Agent:

| Kernel parameter | Agent flag | Value |
|---|---|---|
| `tinkerbell_wg_public_key` | `-wireguard-server-public-key` | Active bootstrap server key, base64 |
| `tinkerbell_wg_endpoint` | `-wireguard-server-endpoint` | Bootstrap device UDP `ip:port` |
| `tinkerbell_wg_prefix` | `-wireguard-prefix` | The `/48` |

None of these are secrets. When they are present the Agent ignores
`grpc_authority`. After a bootstrap server rotation, the Agent saves the
authenticated replacement key and endpoint in
`/run/tink-agent/wireguard-server.json` before switching. On a process restart,
it uses that saved configuration in preference to the original boot parameters
(section 5.12). CaptainOS keeps this file in tmpfs so a reboot uses fresh boot
parameters.

The server's side: the bootstrap device's peer-lookup callback
(`device.SetPeerLookupFunc`) runs when an unknown key sends a handshake
initiation that decrypts with the server's private key. It admits the key with
`AllowedIPs` set to its derived `/128` and nothing else, and records
`address → key` for the interceptor. The callback runs synchronously in
handshake processing, so it only reads memory. It admits every key: anyone with
the server's public key, which is public, can trigger it, and keys are free. The
device already holds at most 65,536 peers (`MaxPeers` in wireguard-go), so the
design bounds retention rather than relying on that cap to distinguish real
Agents from attackers.

Bootstrap peers are just-in-time and live only in the device's memory; nothing
is written to the API:

- **Every bootstrap peer has a fixed maximum lifetime from admission.**
  Handshakes, keepalives, and `Register` calls cannot extend its deadline,
  regardless of the result. At the deadline the server removes the peer and its
  address-to-key mapping. `WAITING` and `GRANTED` peers are subject to this limit
  too. Choose the duration during implementation by measuring handshake retries
  and a bounded `Register` request and response; it must allow a real Agent to
  complete that exchange.
- **Peers that never call `Register` are removed after a few seconds.** A real
  Agent calls `Register` right after its handshake, so these peers need not
  occupy capacity for the full maximum lifetime.
- **Rejected registrations trigger prompt removal.** `NotFound` and
  `PermissionDenied` schedule removal of the peer and its address-to-key mapping
  after a short, bounded grace period for the error response to leave the
  tunnel. Removing the peer inside the handler before returning could prevent
  delivery of that response. Subsequent requests and handshakes cannot postpone
  removal, and the grace period cannot extend the maximum lifetime.
- **Removal does not change identity ownership.** It does not clear a binding,
  change a persistent key, or remove a Workflow session. An Agent can reconnect
  with the same bootstrap key on its next poll, requiring another handshake.
  Response delivery is not guaranteed; if removal cuts off a response, the
  Agent reconnects and retries under the normal retry contract.
- **Handshake flood mitigations do not guarantee availability.** Under load,
  wireguard-go requires a
  cookie round trip, which defeats spoofed source addresses, and rate limits
  handshakes per source IP. Fixed lifetimes prevent callers from retaining peers
  indefinitely, but sustained admission of new keys can still exhaust peer
  capacity or shared server resources.

### 5.3 `Register`

Idle Agents poll `Register` instead of `GetAction`. The retry and status-code
contract in [AGENT_SERVER_RETRY.md](AGENT_SERVER_RETRY.md) applies to it as it
does to `GetAction` today.

On a retiring bootstrap slot, `Register` redirects the caller to the active slot
without granting or re-issuing a session or creating an enrollment Workflow.
A successful response is `WAITING` with `move_to`, even if work is available;
the Agent switches before registering again. Error responses, including
`NotFound` and `PermissionDenied`, carry the same `BootstrapServer` value as a
gRPC status detail because an RPC error has no `RegisterResponse` body. The
Agent handles that authenticated migration information before retrying against
the active slot. A redirect does not authorize the caller or change a binding.

```proto
service AgentService {
  rpc Register(RegisterRequest) returns (RegisterResponse) {}
}

message RegisterRequest {
  string agent_id = 1;
  AgentAttributes agent_attributes = 2; // for discovery and enrollment, moved from ActionRequest
}

message RegisterResponse {
  enum State {
    STATE_UNSPECIFIED = 0;
    STATE_WAITING = 1; // no Workflow work for this Agent yet
    STATE_GRANTED = 2;
  }
  State state = 1;
  Session session = 2;          // set when GRANTED
  BootstrapServer move_to = 3;  // set while this Agent's bootstrap server key is retiring (section 5.12)
}

message Session {
  string workflow = 1;          // namespace/name
  bytes private_key = 2;        // session key, generated for this session
  bytes preshared_key = 3;
  string address = 4;           // the Agent's session tunnel address
  bytes server_public_key = 5;  // session server key
  string server_endpoint = 6;   // session device UDP ip:port
  google.protobuf.Timestamp expires_at = 7;
}

message BootstrapServer {
  bytes public_key = 1;         // the active bootstrap server key
  string endpoint = 2;          // its bootstrap device UDP ip:port
}
```

The caller's bootstrap key isn't in the request. The server takes it from the
tunnel, so a caller can only register the key it holds.

`Register` runs three steps.

**1. Find the Workflow.** A Workflow has work for `agent_id` when it is `PENDING`
or `RUNNING` and its current Task, the first one that hasn't finished, is
assigned to `agent_id`. In a Workflow with several Agents, each Agent gets its
session when its own first Task comes up, not while another Agent's Tasks run
before it.

**2. Identify the caller.** The Hardware decides who its Agent is. A Workflow
decides only for Agents that have no Hardware. Authorization is checked for the
requested `agent_id`; a bootstrap key may be authorized for multiple Agent IDs
(section 5.4):

1. A Hardware exists for `agent_id` and has `spec.agentPublicKey` (section 5.5):
   the caller's key must be that key. Otherwise the server sets
   `AgentKeyConflict` on the Hardware and returns `PermissionDenied`.
2. A Hardware exists for `agent_id` without `spec.agentPublicKey`, and the
   Workflow doesn't list `agent_id` in `spec.agentKeys`: the binding decides,
   in step 3.
3. The Workflow lists `agent_id` in `spec.agentKeys` (section 5.5), and no
   Hardware exists, or only Hardware that auto discovery created and that has no
   `spec.agentPublicKey`: the caller's key must be that key. Otherwise the
   server sets `AgentKeyConflict` on the Workflow and returns
   `PermissionDenied`.
4. No Hardware exists and no Workflow lists `agent_id`: with auto discovery
   enabled, Hardware is created from the attributes, as `Discover` does today,
   and the caller continues as in case 2. Otherwise only auto enrollment can
   proceed (section 5.6), or the server returns `NotFound` and the Agent retries
   with backoff.

**3. Grant a session.** Each Workflow records one session per Agent (section 5.7).

| Workflow | Session record for this Agent | Result |
|---|---|---|
| None | — | `WAITING`, or auto enrollment runs (section 5.6). |
| Found | None | Session granted, binding the caller's key (section 5.4), if the optional source check passes. `GRANTED`. |
| Found | Bound to this key | Session re-issued with a new session key, replacing the old one. Covers a lost response and an Agent restart. `GRANTED`. |
| Found | Bound to another key | `PermissionDenied`. Workflow condition `AgentKeyChanged` set (section 5.8). |

### 5.4 Bindings

A binding says "this key is this Agent, for this Workflow." It's for Agents whose
Hardware doesn't set a persistent key (section 5.5). It isn't a separate object: it
is the `bootstrapKey` in the Agent's session record in Workflow status
(section 5.7).

- **An Agent is bound only while a Workflow has work for it.** An idle Agent
  gets `WAITING` and holds nothing. There is no lease, no renewal, and no
  release: a reboot or a new key between Workflows needs nothing cleared, and
  an attacker can't bind a machine ahead of its Workflow.
- **The first session creates the binding.** The first key to call `Register` for
  `agent_id` while a Workflow has work for it is bound. Writes use the
  Workflow's `resourceVersion`, so two replicas can't both win.
- **It lasts until the Workflow ends.** A binding ends when its Workflow reaches
  a terminal state (`SUCCESS`, `FAILED`, `TIMEOUT`) or is deleted, or when an
  operator rebinds (section 5.8). It doesn't expire in the middle of a Workflow,
  however long its Actions run.
- **Bootstrap keys need not be unique across Agent IDs.** A key may be bound or
  configured as a persistent key for multiple Agent IDs. Each registration must
  independently pass the requested Agent's authorization checks; authorization
  for one Agent gives no permission for another. Each operational session remains
  restricted to one Agent in one Workflow. A bootstrap-key lookup index can
  return multiple records and does not enforce global uniqueness.

**Conflicts.** Another key calling `Register` for a bound Agent gets
`PermissionDenied`, and the server sets `AgentKeyChanged` on the Workflow with
that key and its UDP source address (section 5.8). Bindings exist only while a
Workflow is active, so this is never a stale binding left by an earlier boot:
either the Agent's key changed in the middle of the Workflow, or two keys claim
the same Agent.

**No head start.** An Agent that is already waiting when its Workflow appears
has no advantage: it and any other caller race for the first session, and a caller
that polls faster usually wins. Most Workflows start by booting the machine, so
its Agent's key is new either way. A persistent key removes the race.

**Optional source check.** With `--wireguard-binding-source-check`, a key can be
bound only if its UDP source IP, as seen by the bootstrap device, is one of the
Hardware's `spec.interfaces[].dhcp.ip.address`: the address Smee gives that
machine. An attacker then has to take over that exact address on that segment,
which is the trust Smee relies on today, and from then on the key decides.
Re-issued sessions and rebinds (section 5.8) skip the check. It doesn't apply to
Hardware that `Register` creates through discovery, because the first caller
defines that Hardware. It's off by default because it fails when NAT sits between
the Agent and the server, or when the Agent reaches the server from an address
that isn't in the Hardware's spec. It's meaningful only in Smee's DHCP
`reservation` mode, where that address is the one the machine is given. In
`proxy` and `auto-proxy` modes another DHCP server assigns addresses, so the
Hardware's address may be absent or not the one in use, and the check fails or
can't be configured.

### 5.5 Persistent keys

A persistent key survives reboots, because the machine provides it or because
the Agent keeps it on persistent storage, and an operator sets it ahead of time.
An Agent with one doesn't need a binding. The key is set in one of two places:

```yaml
# Hardware: the machine's Agent, in every Workflow
spec:
  agentID: 3c:ec:ef:4c:4f:54
  agentPublicKey: <bootstrap public key, base64>
---
# Workflow: Agents that have no Hardware, in this Workflow only
spec:
  agentKeys:
    netbox-setup: <bootstrap public key, base64>
```

- Only the persistent key is accepted. There is no binding and no first-use
  race.
- Both fields mean "only this key is accepted," whether or not the key actually
  survives reboots. Auto enrollment, for example, sets a boot's generated key in
  `spec.agentKeys` (section 5.6).
- **The Hardware always decides who its Agent is.** A Workflow can't list a key
  for an Agent that has Hardware. If it does, the server sets the Workflow
  condition `AgentKeysInvalid`, ignores that entry, and identifies the Agent by
  its Hardware as usual. Otherwise anyone who can create a Workflow could make
  any key act as any machine's Agent. Creating a Workflow decides what runs on a
  machine, not who that machine is.
- If Hardware is later created for an Agent a Workflow lists, the Hardware takes
  over the same way.
- **Except Hardware that auto discovery created** and that still has no
  `spec.agentPublicKey`. It doesn't override a Workflow's `spec.agentKeys`
  entry. Otherwise anyone could call `Register` for an `agent_id` before its
  Workflow exists, have discovery create Hardware for it, and so void the key
  the operator set. Discovery marks the Hardware it creates.
- A reboot keeps the key, so a Workflow continues after a reboot automatically:
  the session record names the same key (section 5.7).
- An Agent without Hardware, such as an administrative Agent that sets up the
  network, must be listed in `spec.agentKeys`, unless auto enrollment created its
  Workflow, which lists it automatically (section 5.6).
- Changing a persistent key hands the Agent over to the new key (section 5.8).
- Whoever can write Hardware and Workflows already decides what runs where.
  These fields add which key runs it.

**Where a persistent key comes from.** The Agent loads its key from
`-wireguard-key-file` and logs the public key at startup. WireGuard needs an
X25519 private key that the Agent process can use, so:

- **TPM.** Seal the key to the TPM as a persistent object, optionally bound to
  PCR values, and unseal it to the key file at boot. The key survives disk wipes
  and reboots, and only that machine, in an approved boot state if PCRs are
  used, can unseal it. Shipping TPMs offer NIST curves, not X25519, so the TPM protects
  the key at rest rather than performing the handshake: the unsealed key is in
  the Agent's memory and key file while it runs. CaptainOS needs a unit that
  unseals before the Agent starts and then extends a PCR in the sealing policy,
  so that nothing later in the boot, including Actions, can unseal it again.
- **Persistent storage.** An Agent that isn't on CaptainOS, such as an
  administrative Agent, points the flag at a mounted Secret or volume.
- **HSMs and hardware security keys** whose private key can't leave the device
  aren't supported (section 9).

Setting a persistent key records the operator's trust in it. It doesn't prove the key is
held by a TPM; attestation would (section 12).

### 5.6 Auto enrollment

Today, when an Agent has no Workflows at all, `GetAction` matches its reported
attributes against WorkflowRuleSets and creates an `enrollment-<agentID>`
Workflow, with or without Hardware
([enrollment.go](../../../tink/server/internal/grpc/enrollment.go)). Enrollment
supports only single-Agent templates.

With this design:

- Enrollment runs in `Register` instead of `GetAction`, under the same trigger.
  The Hardware's `spec.auto.enrollmentEnabled` still applies.
- The created Workflow is granted to the enrolling key in the same `Register`
  call, so that key is bound (section 5.4). An Agent with a persistent key must
  enroll with it. An Agent without Hardware is also listed in the Workflow's
  `spec.agentKeys` with the enrolling key. From then on, only that key can run
  the Workflow, so it can't be taken over.
- The enrollment Workflow must not become eligible for session grants until
  ownership by the enrolling key has been recorded. Concurrent registrations
  cannot claim it during creation or initialization; performing creation and
  binding in the same RPC is not by itself sufficient to guarantee this.

What WireGuard can't fix: enrollment trusts the first caller. The attributes it
matches are reported by the Agent itself, so anyone who can reach the bootstrap
tunnel can fake them, match a WorkflowRuleSet, and receive that template's
Actions, including any secrets in them. That's true today too. WorkflowRuleSets
should not reference templates that carry secrets, and operators who can't
accept this should leave auto enrollment off.

### 5.7 Workflow sessions

A session lets one Agent run its Tasks in one Workflow. A Workflow whose Tasks name
two Agents has two sessions. The server issues a session when `Register` identifies
the caller (section 5.3) and finds work for it. The Workflow must be initialized
and ready to execute before any session is granted.

The first operational session grant starts the Workflow's execution clock.
In the same atomic Workflow status update as that grant, the server records
`executionStartedAt` from its clock and sets
`executionDeadline = executionStartedAt + globalTimeout`. Preparation before
the first grant does not consume this budget; session establishment, fetching
the first Action, and execution do. The deadline is fixed for the rest of the
Workflow. Later grants, session re-issuance, and rebinds cannot extend it.

To issue a session:

1. Select the active session server slot and generate a session key pair.
2. Derive the pre-shared key: `HMAC-SHA256(PSK root, Workflow UID || session
   public key)`. Every session has its own session key, so each pre-shared key
   is unique to one Agent in one Workflow; a re-issued session gets a new one. The
   root is in the key Secret, so every replica can compute it without the
   pre-shared key being stored.
3. Write the session record to Workflow status, using `resourceVersion` so only
   one session per Agent wins. Set `expiresAt` to the Workflow's execution
   deadline. For the first grant, establish the execution timestamps in this
   same update. If concurrent grants conflict, retry against the recorded
   deadline rather than starting another clock. Do not grant or re-issue a
   session at or after that deadline:

```yaml
status:
  executionStartedAt: "2026-10-22T20:10:00Z"
  executionDeadline: "2026-10-22T22:10:00Z"
  agentSessions:
    - agentID: 3c:ec:ef:4c:4f:54
      bootstrapKey: <base64>           # the bound key (section 5.4)
      source: 192.0.2.10:41641         # UDP source address when bound
      bootstrapSlot: a                 # bootstrap slot it registered on (section 5.12)
      sessionKey: <base64>
      sessionSlot: b                   # session server slot selected at issuance (section 5.12)
      address: fdxx:xxxx:xxxx:1:hhhh:hhhh:hhhh:hhhh
      issuedAt: "2026-10-22T20:10:00Z"
      expiresAt: "2026-10-22T22:10:00Z" # the fixed Workflow execution deadline
      endedAt: null                    # set when the session key is removed
```

4. Return the private key and pre-shared key, together with the selected session
   slot's server public key and endpoint, in the response. The server doesn't
   store the private key anywhere. Re-issuance selects the active session slot
   again and updates `sessionSlot` along with the replacement session key.

The session address is derived from the session public key, like the
bootstrap address. The session device's peer-lookup callback admits a key
only if an active session in the informer cache names it and its `sessionSlot`
matches that device's slot, with that session's `/128`, pre-shared key, and the
hybrid handshake. Until the cache has the new session, the
Agent's handshake is dropped, and WireGuard retries it every 5 seconds.

A session's key is removed when:

- **its Agent's last Task in the Workflow finishes,**
- **the Workflow enters `POST`, `SUCCESS`, `FAILED`, or `TIMEOUT`, or is
  deleted,**
- **`expiresAt` passes,** or
- **an operator hands the Agent over** (section 5.8), or
- **a re-issued session replaces it.**

`expiresAt` in status and `expires_at` in the response are an authoritative
upper bound, not a hint or a promise of access until that time. Every session
in the Workflow has the same expiry, including sessions issued to later Agents
and replacement sessions. Earlier revocation can shorten a session's validity.
There is no separate session timeout or renewal.

At the execution deadline the Workflow times out, even if no Action has started.
Every replica independently rejects session admission and authorization at or
after `expiresAt` and removes the peer, without waiting for a Workflow timeout
update. This also prevents a delayed timeout transition from extending access.

Every replica watches Workflows and calls `device.RemovePeer` for a removed key.
A replica stops accepting an early-revoked key when its Workflow cache sees the
change, so a lagging replica accepts it a little longer, but never past its
recorded expiry. A leaked session key is useless once
removed, and never works for another Workflow or another Agent.

The session record stays in Workflow status after its key is removed. Its
`bootstrapKey` is the binding, so until the Workflow ends only that key can
be granted again: after an Agent restart, or after a reboot when the key is
persistent. Another key, such as the next boot's generated key, gets
`AgentKeyChanged` instead (section 5.8).

The Agent keeps its session up until the server removes the key. It polls
`GetAction` on the session, including while another Agent's Tasks run between
its own, and doesn't call `Register`. It returns to `Register` only when
requests on the session fail, which is what happens once the key is removed,
and learns there whether it has another session.

### 5.8 Restarts and key changes

**Agent restart** (crash, OOM kill, upgrade), without a reboot: the Agent reloads
its key and any saved bootstrap server configuration from `/run`, so its session
record still names it. If its server slot has retired and it missed the migration
information, it must obtain fresh boot parameters as described in section 5.12.
Otherwise, `Register` re-issues its session, and `GetAction` re-serves the Action that was
in progress, as it already does after a server restart. The interrupted Action
runs again. Nothing opens a window for another key.

**Reboot with a persistent key** (section 5.5): the same key comes back, so this works
like an Agent restart, after the reboot.

**New key in the middle of a Workflow** (a reboot without a persistent key, or a
replaced key): the Workflow is never handed to another key automatically.
`Register` from the new key returns `PermissionDenied` and sets `AgentKeyChanged`
on the Workflow, with the Agent ID, the new key, and its UDP source address. Left
alone, the Workflow ends at its timeout.

To continue it, an operator hands the Agent over to the new key:

- **Agent with Hardware but no persistent key:** rebind it with an annotation on
  the Hardware.

  ```yaml
  metadata:
    annotations:
      tinkerbell.org/agent-rebind: "<new bootstrap key, base64>"
  ```

  The server moves this Agent's session records in `PENDING` and `RUNNING`
  Workflows to that key and removes their session keys. Then it removes the
  annotation, clears `AgentKeyChanged`, and records an Event. An empty value
  clears the records' bound key and removes their session keys without
  naming a new key, so the next key to `Register` is bound.
- **Agent with a persistent key:** change `spec.agentPublicKey` on its Hardware, or,
  for an Agent without Hardware, its entry in the Workflow's `spec.agentKeys`.
  The server moves the affected session records the same way and clears
  `AgentKeyConflict` and `AgentKeyChanged`.

The named key's next `Register` gets a new session, and `GetAction` re-serves the
interrupted Action. Because the operator names one key, no race opens.

**Evicting an attacker.** The same rebind is the response to `AgentKeyChanged`
when an attacker won the first session: rebind to the real Agent's key, which the
condition shows. The other key loses its sessions and can't be granted again while
the session records name the real key. Banning the key itself would add little,
because keys are free.

**Conditions.** None of them stop a Workflow; they report.

| Condition | On | Set when | Cleared when |
|---|---|---|---|
| `AgentKeyConflict` | The Hardware or Workflow that sets the persistent key | Another key calls `Register` for that `agent_id`. Records the key and its UDP source. | The persistent key on that object changes |
| `AgentKeyChanged` | Workflow | Another key calls `Register` for an Agent bound in that Workflow. Records the key and its UDP source. | A rebind, or the Workflow ends |
| `AgentKeysInvalid` | Workflow | `spec.agentKeys` names an Agent whose Hardware decides (section 5.5) | The entry is removed |

If the final Action reboots the machine before reporting, the session's key lives
until the Workflow times out, but it existed only in the old boot's Agent
process.

### 5.9 Authorization

An interceptor runs on every request that arrives through a tunnel. It finds the
key from the source address, then applies:

| Request | Arrives on | Allowed when |
|---|---|---|
| `Register` | Bootstrap | Always reaches the handler, which applies section 5.3 |
| `GetAction` | Session | The key's session is active and `AgentId` equals the session's `agentID`. Only the session's Workflow is served. |
| `ReportActionStatus` | Session | Same, and the report names the session's Workflow and a Task assigned to that Agent |
| Syslog | Session | The key's session is active |

Anything else gets `Unauthenticated` or `PermissionDenied`, or is dropped for
syslog. The bootstrap device serves no syslog.

The Workflow check uses the session key. The tunnel address only locates
the key; WireGuard already guarantees that one address maps to one key, and the
server records the address in the session for syslog attribution and logs. `AgentId`
remains as a consistency check and for the existing indexes.

### 5.10 Agent lifecycle

1. CaptainOS boots. `tink-agent-setup` reads the `tinkerbell_wg_*` parameters,
   and rsyslog forwards to the Agent's local syslog forwarder.
2. The Agent loads its key (a persistent key, or the one left in `/run` by an earlier
   run) or generates one, brings up the bootstrap tunnel, and starts its syslog
   forwarder (section 5.11).
3. It polls `Register`. Typical results are `NotFound` (unknown Agent),
   `WAITING` (nothing to run yet), and `GRANTED`.
4. On `GRANTED` it brings up a session device with the issued key and runs
   its Tasks over it with `GetAction` and `ReportActionStatus`, as today.
5. It keeps the session and polls `GetAction` on it, without calling
   `Register` (section 5.7). When requests on the session fail, because the
   server removed the key or the tunnel broke, it tears the session device down
   and goes back to step 3.

The Agent never says goodbye. Its bootstrap peer expires, and its binding and
sessions end with its Workflow.

### 5.11 Syslog through the tunnel

The tunnels exist only inside the Agent process, so the Agent forwards local
syslog traffic into them. In CaptainOS, rsyslog sends to `127.0.0.1` when the
`tinkerbell_wg_*` parameters are set. rsyslog starts before the Agent, so it
should forward over TCP with an in-memory queue, which holds early boot messages
until the Agent's forwarder is listening. The forwarder sends each message as a
UDP datagram to `:514` in the session tunnel while granted. Before a session,
and between sessions, it keeps messages in a bounded buffer, dropping the oldest,
and sends the buffer once granted. Nothing goes over the bootstrap tunnel, so an
unauthenticated key can't write to the server's logs.

On the server, Smee's syslog receiver
([receiver.go](../../../smee/internal/syslog/receiver.go)) binds its own UDP
socket from an address string. It needs to also accept a packet connection from
the tunnel, and to tag messages with the Agent ID, and the Hardware when there is
one, instead of the source IP.

### 5.12 Server keys and rotation

The server holds a set of keys. Each tier has two slots, `a` and `b`, each with
its own device and UDP port, so a new key can come up next to the old one:

| Tier | Slot `a` | Slot `b` |
|---|---|---|
| Bootstrap | `51820` | `51821` |
| Session | `51822` | `51823` |

The Secret stores, per slot, the private key and a state: `active`, `retiring`,
or empty. For a retiring bootstrap slot it also stores the migration deadline,
once set, so all replicas use the same deadline across restarts. It also stores
the `/48` and the PSK root.

To rotate a tier, generate a key in the empty slot and make it `active`. The old
slot becomes `retiring`.

- **Bootstrap.** Smee advertises the active slot from then on. Agents still on
  the retiring slot receive the active key and endpoint through `move_to`,
  including in RPC error details (section 5.3). That arrives over the old tunnel,
  so it's authenticated. The Agent saves it before switching its bootstrap
  tunnel, without changing its own key. The retiring slot grants no new sessions
  and does not re-issue existing ones; callers must register on the active slot.
  An Agent in a session doesn't call `Register`, so it can't learn of the
  rotation until its session ends. Keep the retiring slot available while any
  active session record names it in `bootstrapSlot`. Once no active session
  references it, start a bounded migration grace period; if none reference it
  when rotation begins, start the grace period immediately. Choose the grace
  duration during implementation to allow normal session-failure detection,
  `Register` retries, and migration. Remove the slot at the deadline regardless
  of bootstrap peer count or activity. Handshakes and registrations cannot
  extend the deadline. A long Workflow delays the start of the grace period,
  not the time its Agent has to migrate afterward.
- **Session.** New sessions use the active slot. The retiring slot is removed
  when no active session record names it in `sessionSlot`. Every replica uses
  this persisted field for admission and retirement accounting, including after
  a restart. `bootstrapSlot` cannot substitute for it because the two tiers
  rotate independently.

**Missed bootstrap migration.** A process restart uses the saved server
configuration if the Agent received `move_to`. An Agent that was down throughout
the migration window and still knows only the retired server must reboot through
a boot path that supplies current Smee parameters. An old ISO or other cached
boot configuration must be refreshed too. There is no separate discovery service
or automatic fallback to an unauthenticated server key. This is an accepted
recovery limitation of finite retirement. Rebooting without a persistent Agent
key also requires an operator rebind to continue an active Workflow (section 5.8).

**Emergency bootstrap retirement.** An operator can force removal of a retiring
bootstrap slot before its sessions drain or its grace period ends. This
intentionally sacrifices seamless migration. Existing operational sessions are
not revoked by removing a bootstrap slot, but affected Agents may need fresh
boot parameters when they next register, and a reboot without a persistent key
may require a rebind.

Only one rotation per tier can be in progress at a time.

### 5.13 Modes

`--wireguard-mode`:

| Mode | Plain gRPC and syslog | Tunnels | Authorization |
|---|---|---|---|
| `disabled` (default) | Yes | No | None, as today |
| `optional` | Yes, for Agents without a persistent key or a binding | Yes | Enforced in the tunnels, and on the plain path for Agents with one |
| `required` | No; gRPC and syslog only in the tunnels | Yes | Enforced |

`optional` lets CaptainOS images move over one at a time. In `optional` mode the
plain listener refuses requests for an `agent_id` that has a persistent key or a
binding. An Agent without a persistent key is bound only while a Workflow has
work for it (section 5.4). Between Workflows, and when its next Workflow appears
until it registers, anyone can still use its `agent_id` on the plain path, as
today, and nothing reports it. Only `required` closes the plain path, so
`optional` is for migration, not a resting state.

### 5.14 Configuration

Tinkerbell, in a new `wireguard` flag section:

| Flag | Default | Purpose |
|---|---|---|
| `--wireguard-mode` | `disabled` | Section 5.13 |
| `--wireguard-bootstrap-ports` | `51820,51821` | Bootstrap slot ports |
| `--wireguard-session-ports` | `51822,51823` | Session slot ports |
| `--wireguard-key-secret` | `tinkerbell-wireguard` | Secret holding keys, slot states, `/48`, PSK root |
| `--wireguard-binding-source-check` | `false` | Section 5.4 |

API additions: Hardware `spec.agentPublicKey`, Workflow `spec.agentKeys` and
`status.agentSessions`, the `AgentKeyConflict`, `AgentKeyChanged`, and
`AgentKeysInvalid` conditions, and the `tinkerbell.org/agent-rebind`
annotation. Hardware gets no status field: bindings live in the session records.

Helm exposes all four UDP ports on the Tinkerbell Service. Smee reads the
active bootstrap key and endpoint to write the kernel parameters.

Agent: the three flags in section 5.2, `-wireguard-key-file`, and the syslog
forwarder listen address. CaptainOS `tink-agent-setup` parses the kernel
parameters, passes them on with `-wireguard-key-file=/run/tink-agent/wireguard.key`,
and points rsyslog at the forwarder. On machines with a TPM-sealed key, a
CaptainOS unit unseals it to that path before the Agent starts.

## 6. Security

The attacker sits on the provisioning network. They can sniff traffic, spoof MAC
and IP addresses, fetch iPXE scripts, and send anything to Tinkerbell's ports.
They can't compromise the Tinkerbell control plane or the Kubernetes API.

| Attack | Today | With this design |
|---|---|---|
| Read Actions and their secrets in transit | Possible without TLS | Encrypted |
| Pose as another Agent to fetch its Actions | Succeeds | Needs that Agent's session, which goes only to its bound or persistent key |
| Pose as an Agent with a persistent key | Succeeds | No. Only the persistent key is accepted, and there is no binding to race for. |
| Report false Action status | Succeeds | Needs the session |
| Take over a running Workflow | Succeeds | No. Each session record names one bootstrap key, and only an operator can move it. |
| Use a captured session key later | n/a | No. It's removed when its session ends. |
| Reach the Workflow service with any other key | Succeeds | No. The session device admits only granted keys. |
| Forge another machine's syslog | Spoof its IP | No. Messages are attributed by key. |
| Get a Workflow through discovery or enrollment | Succeeds | Still succeeds when those are enabled (section 5.6). The resulting Workflow belongs to the caller's key, so it can't be taken from them, but nothing proves who they are. |
| Win a Workflow's first session | n/a | Only for an Agent without a persistent key, and only between the Workflow having work for it and the real Agent's first `Register`. With the source check on, also only from that Hardware's address. The real Agent then gets `AgentKeyChanged`, and the operator rebinds to the real key. |
| Bind an idle machine ahead of its next Workflow | n/a | No. Nothing is bound until a Workflow has work for the Agent. |
| Flood the bootstrap device | n/a | Cookies and per-IP handshake rate limiting mitigate floods. Every bootstrap peer has a fixed maximum lifetime; missing or rejected registrations trigger earlier removal (section 5.2). Running Workflows use a separate session device, but sustained floods can still exhaust bootstrap capacity or shared server resources. |
| Change the iPXE script to swap the server key | Can already swap the kernel and initramfs | Unchanged. HTTPS iPXE is the mitigation for both. |

Residual risks:

- **Bootstrap availability is not guaranteed.** A caller cannot extend a peer's
  lifetime by calling `Register` or renewing handshakes, but can continually
  reconnect with fresh keys. Retained state depends on admission rate and peer
  lifetime; sufficiently high sustained admission can still deny service.
- **Trust on first use** for Agents without a persistent key. An attacker who calls
  `Register` first after a Workflow appears gets that Workflow's session, and an
  Agent that was already waiting has no head start (section 5.4). A
  persistent key removes this; otherwise the source check narrows who can bind, and
  `AgentKeyChanged` and rebind are the response.
- **Auto enrollment trusts the first caller** and self-reported attributes
  (section 5.6).
- **`optional` mode leaves the plain path open** for Agents without a persistent
  key between Workflows, and until they register for a new one (section 5.13).
- **`AgentKeyChanged` doesn't stop an attacker who bound first.** By design, it
  is only reported, so a session already issued to the wrong key stays active
  until an operator rebinds. Failing the Workflow instead would let anyone who
  knows an `AgentId` stop it.
- **Write access to Hardware and Workflows authorizes Agents,** through the
  rebind annotation, `spec.agentPublicKey`, and `spec.agentKeys`. The key Secret
  is a trust anchor too.
- **A persistent key is trusted as set.** Nothing proves it's held by a TPM, or
  that the key file wasn't copied off the machine.
- **Reusing a bootstrap key shares its compromise blast radius.** A stolen key
  can obtain sessions for every Agent ID that authorizes it. Independently
  generated or machine-specific persistent keys are recommended for physical
  machines, but global key uniqueness is not enforced.
- **The server knows each session private key** when it issues it. That
  doesn't weaken anything, because the server is the only party that trusts the
  key, and it doesn't store it.
- **Actions run with the Agent's access.** Any Action can send syslog through
  the forwarder, as it can today. Privileged Actions can also read the Agent's
  key file or memory.

## 7. Dependencies and footprint

- `github.com/tailscale/wireguard-go` (tailscale branch) and
  `gvisor.dev/gvisor`, already on the `secrets` branch. The fork's
  `PeerLookupFunc` now returns `(*NewPeerConfig, bool)`, with per-peer
  pre-shared key and hybrid settings, so `pkg/wireguard` must move to that API.
- No `tailscale.com` and no DERP relay.
- The Agent binary grows. Measure it before CaptainOS ships it.
- Agents need direct UDP to the server. There's no NAT traversal beyond the
  Agent initiating and keeping the mapping alive.

## 8. Operations

- **Replicas.** Bindings and sessions are in the API, the Secret is shared, and
  pre-shared keys are derived. So any replica can serve any Agent, if the load
  balancer keeps each Agent's UDP flow on one replica. Every replica watches
  Workflows to remove ended keys.
- **API writes.** Idle Agents cost none. Sessions, and the bindings in them, cost
  one Workflow status write per Agent per Workflow, plus one per re-issue.
- **MTU.** The tunnel MTU is 1420. Underlay networks with less than 1500 bytes
  need a lower value.
- **Metrics.** Peers per device, bootstrap peers removed by reason (maximum
  lifetime, no `Register`, rejected registration), bindings, conflicts, source
  check failures, sessions issued and removed, rebinds, and authorization denials
  by request.

## 9. Alternatives considered

- **One device for both layers,** with the interceptor alone keeping bootstrap
  keys away from the Workflow service. Fewer ports, but a bug in one check would
  expose Workflows, and a flood of bootstrap handshakes would share a device
  with running Workflows.
- **The Agent's bootstrap key as its only key.** No server-issued key, so no
  per-Workflow credential that dies with the Workflow.
- **The Agent generates its session key** and sends the public half. No
  stronger, because the server is the only party that trusts the key, and it
  adds a key exchange step.
- **Idle bindings:** bind an Agent to its Hardware before a Workflow exists,
  with a lease the Agent renews. Rejected. An attacker could bind a powered-off
  or idle machine ahead of its next Workflow. It needs a lease, renewals, and a
  Hardware status write per idle Agent; a reboot waits for the lease; and a
  release call can't cover a BMC hard power-off. It only helps an Agent that is
  already waiting when its Workflow appears, and a persistent key covers
  that.
- **Smee netboot ends a binding.** Rejected: any machine on the network can make
  a netboot request, so this would let anyone reopen the binding window.
- **Hand a Workflow over to a new key automatically** after a reboot. Rejected:
  whoever registered first after the reboot would get the rest of the Workflow.
- **A policy ConfigMap** for pinned keys and a deny list. Rejected: pinned keys
  belong with the Workflow they authorize, and a deny list adds little, because
  keys are free and addresses can change. Rebinding evicts a key.
- **A Workflow handover annotation.** Not needed: rebinding the Hardware or
  editing a persistent key moves the session.
- **The device performs WireGuard's private key operations,** so the key never
  leaves it. wireguard-go uses the static private key in about four places: once
  per peer, then on every handshake. A patch could delegate those to a device,
  but Tinkerbell would carry it on top of Tailscale's fork. That is what a
  "wireguard-go plus tpm2-tss" design needs: the static key is used for X25519
  Diffie-Hellman on every handshake, not for signing, so the TPM would have to
  perform X25519 ECDH (`TPM2_ECDH_ZGen`). Recent TCG specifications add
  Curve25519 (`TPM_ECC_CURVE_25519`), but shipping TPMs implement only NIST
  curves, as do most HSMs (YubiHSM 2, for example); YubiKey 5.7+ PIV and a few
  PKCS#11 HSMs do support it. Not pursued until TPMs with Curve25519 ship. Then
  only the Agent changes: Hardware still sets the public key in
  `spec.agentPublicKey`.
- **A key derived deterministically by the device:** an HMAC, under a key that
  never leaves the TPM, HSM, or security key, of a fixed label, turned into an
  X25519 key. It needs no stored blob and works with any HMAC-capable device,
  but the derived key is in the Agent's memory like a sealed key. Not pursued.
- **The device signs each boot's WireGuard key** at `Register`, against a
  device public key the Hardware lists. It keeps every long-term secret in the
  device and works with any TPM or HSM, but needs a signature step in `Register`
  and a second key type on Hardware. Not pursued.
- **Tinkerbell delivers each Agent's key** on the kernel command line, in a
  per-host initramfs, or on BMC virtual media. Each delivery path is weaker than
  a key generated on the machine, or works only with virtual-media boot.
- **tailcat.** The same WireGuard model plus NAT traversal, but it needs a DERP
  relay, pulls in `tailscale.com`, has no API or wire stability promise, and its
  threat model doesn't yet cover hostile peers.
- **mTLS.** Not pursued.

## 10. Implementation phases

1. **`pkg/wireguard`.** Move the `secrets` branch package onto the current fork
   API. Remove the hardcoded addresses, paths, ports and DNS. Add address
   derivation, the hybrid handshake, and tests.
2. **Server devices.** Both tiers, the key Secret with slots, admission
   callbacks, the shared device component in `cmd/tinkerbell`, flags, `optional`
   mode. Fix `NewTunnelListener` being called from two places in `cmd.go`.
3. **Bindings and `Register`.** First-session binding in Workflow status, the
   bootstrap key index supporting multiple records per key, the source check,
   discovery moved into `Register`, and the rebind annotation.
4. **Sessions and persistent keys.** Hardware `spec.agentPublicKey`, Workflow
   `spec.agentKeys`, per-Agent session records and key index, key issuance, derived
   pre-shared keys, the session admission callback, `RemovePeer` on session
   end, the interceptor, and `AgentKeyChanged`. Establish the Workflow execution
   clock atomically with its first session grant and enforce the fixed deadline
   in both Workflow timeout handling and session authorization.
5. **Enrollment.** Move it into `Register`, grant the created Workflow's session
   to the enrolling key, and set `spec.agentKeys` on Workflows it creates for
   Agents without Hardware.
6. **Agent.** Key file, bootstrap and session tunnels, the `Register` loop,
   session switching, and the syslog forwarder. Measure binary size.
7. **Syslog on the server.** Tunnel listener and attribution by key.
8. **CaptainOS and Smee.** Kernel parameters, `tink-agent-setup`, rsyslog
   forwarding, an optional TPM unseal unit, Helm ports.
9. **Rotation, `required` mode,** docs, and end-to-end tests: boot an Agent,
   bind, run a Workflow with a second Agent listed in `spec.agentKeys`, restart
   the Agent mid-Action, reboot an Agent with a persistent key mid-Workflow, rebind
   to a new key, enroll an Agent without Hardware, and check that other and
   ended keys are refused.

## 11. Decisions

| Question | Decision |
|---|---|
| Explicit `Register` RPC, or bind on the first `GetAction`? | Explicit `Register` |
| What is an Agent's tie to its key called? | A binding |
| Where do bindings and sessions live? | Both in Workflow status: the binding is the session record's bootstrap key |
| Must a bootstrap key be unique across Agent IDs? | No. Each Agent is authorized independently, and each operational session is scoped to one Agent in one Workflow. Separate machine keys are recommended to limit compromise blast radius. |
| Bindings outside a Workflow? | No. An Agent is bound only while a Workflow has work for it (section 5.4). |
| Agents with Tasks but no Hardware? | Listed with their key in the Workflow's `spec.agentKeys` |
| Hardware key or Workflow key: which wins? | The Hardware, always. A Workflow can't list a key for an Agent that has Hardware. |
| Workflows with Tasks for several Agents? | One session per Agent per Workflow |
| When does the Workflow execution timeout start? | At the first operational session grant, atomically with its session record. All sessions expire at the same fixed Workflow deadline; re-issuance and rebinds do not extend it. |
| New configuration objects (policy ConfigMap)? | None |
| Auto enrollment? | Moves into `Register`. Agents without Hardware may enroll; the Workflow is pinned to the enrolling key. |
| Can a Smee netboot end a binding? | No. It would reopen the window for anyone on the network. A binding ends with its Workflow (section 5.4). |
| Hybrid post-quantum handshake? | On, for both devices |
| Multiple server keys? | Yes. Two slots per tier for rotation (section 5.12). |
| HookOS? | Deprecated. CaptainOS only. |
| Syslog through the tunnel? | Yes, session tunnel only; buffered until granted (section 5.11) |
| Tootles through the tunnel? | No. Its clients are installed OSes, which have no tunnel. |
| Fail the Workflow on `AgentKeyConflict` or `AgentKeyChanged`? | No. They are only reported. |
| Agent restart in the middle of a Workflow? | Continues automatically: the key is kept in `/run` |
| Machines with a TPM or other persistent key? | Set in Hardware `spec.agentPublicKey`: no first-session race, and reboots continue automatically. The key comes from a TPM-sealed or persistent key file; keys held or derived by a device aren't pursued (section 9). |
| Agent release call? | None. Bindings end with their Workflow or by rebind; there is nothing to release between Workflows. |
| New key in the middle of a Workflow? | Never automatic. An operator rebinds or edits the persistent key. |
| Source IP check? | Optional, off by default |
| Deny list? | No. Rebinding evicts a key. |

## 12. Future hardening

- **Manual approval.** A binding stays pending until an operator approves it,
  like kubelet CSR approval. Removes trust on first use at the cost of a manual
  step per Workflow.
- **One-time enrollment token.** Smee puts a single-use random value in the
  kernel parameters for each boot, and `Register` must present it to bind.
  Narrows the window to whoever fetched that boot's script.
- **TPM attestation.** `Register` carries a TPM quote proving that the persistent
  key was unsealed by that machine's TPM in an approved boot state, checked
  against an endorsement key the Hardware lists. Turns a persistent key from
  operator trust into proof.
